# 02 — Модель данных и архитектура

Здесь описано, **как хранить данные**, чтобы три ваших листа (Сделки, Закрытые
сделки, Портфель) перестали быть тремя ручными таблицами и стали одной базой,
из которой всё остальное считается автоматически.

---

## 1. Главная идея: одна таблица истины

Сейчас у вас три листа, и два из них (Закрытые сделки, Портфель) вы фактически
поддерживаете руками, дублируя данные. Это источник ошибок.

**Правильно так:** есть **один** источник истины — журнал операций (лист «Сделки»).
Всё остальное — **вычисляемые представления**, которые программа строит сама:

```
                    ┌────────────────────┐
                    │  ОПЕРАЦИИ (журнал)  │   ← единственное, что вы вводите/импортируете
                    │  = ваш лист «Сделки» │
                    └──────────┬─────────┘
                               │  движок расчётов (пересчёт при любом изменении)
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
      ┌─────────────┐  ┌──────────────┐  ┌──────────────┐
      │  ПОЗИЦИИ     │  │  СДЕЛКИ      │  │  ПОРТФЕЛИ    │
      │ (открытые)   │  │ (закрытые)   │  │  (сводка)    │
      │ = «Портфель» │  │ = «Закрытые» │  │  = итоги     │
      └─────────────┘  └──────────────┘  └──────────────┘
        вычисляется       вычисляется        вычисляется
```

Вы больше **не заполняете** «Портфель» и «Закрытые сделки» руками — они всегда
пересчитываются из журнала операций. Ввод только в одном месте.

---

#### Идентичность инструментов (`instrument_identifiers`)

Один актив приходит из разных источников (xlsx, HTML, CSV, API Т-Банка) под разными
кодами: `TMON` (xlsx) и `TMON@` (API, «Денежный рынок»), `RU000A10B4K3` и внутренний код
брокера `TCS00A10B4K3`. Раньше `ensureInstruments` искал совпадение по тикеру/ISIN/названию,
не находил и заводил дубль без цены. Теперь два разных механизма:

| | Нормализация кода | Сопоставление идентичностей |
|---|---|---|
| Природа | детерминированное правило (`TMON@` → `TMON`) | решение человека или сильный идентификатор |
| Где живёт | код: `libs/core/instrument-identity.ts` (чистые функции) | данные: таблица `instrument_identifiers` |
| Когда | ко всем строкам ВСЕХ источников до резолва (`normalizeRawRows`) | при резолве инструмента |

**Конвейер:** `парсер → normalizeRawRows (@core) → planInstrumentIdentities (@core) → preview/commit`.
Шаг нормализации один и стоит там, где сходятся все источники (`ImportService.stashRawRows`:
и файлы, и синк Т-Банка), а не в каждом парсере. Правила — список маленьких чистых функций
(срезать хвостовой `@`, trim, верхний регистр); требования: детерминированность, идемпотентность,
независимость от источника. Специфика брокера (`TCS00…`) — не нормализация.

**Идентификаторы в `RawRow`.** `ticker` — только биржевой тикер; остальное — `identifiers`:
`isin` (только валидный), `figi`, `tbankUid`, `brokerCode` (внутренний код, не ISIN). Валидатор
ISIN один (`isValidIsin`: формат + код страны ISO 3166 + контрольная цифра по Луну) — отсекает
`TCS00A10B4K3` и СЕКОД `SU52002RMFS1`. Невалидный «ISIN» становится `brokerCode`.

**Таблица `instrument_identifiers`:** `(scheme, value) PK`, `instrument_id → instruments ON DELETE CASCADE`,
`origin` (`import` | `merge` | `manual`), `created_at`. Схемы: `ticker | isin | figi | tbank_uid |
broker_code | name`. Схема + значение, а не голый «alias»: `TMON` как тикер и как код брокера — разные
факты. Не колонки в `instruments` (у актива много кодов и нужно происхождение связи); `instruments.ticker`
и `isin` остаются отображаемыми полями, резолв идёт только через эту таблицу. Заполняется из
существующих инструментов после миграций (идемпотентно; название нормализуется в TS — SQLite не умеет
`lower()` для кириллицы).

**Резолв** (`planInstrumentIdentities`, чистая функция; preview — dry-run, commit применяет тот же план).
Порядок силы: `tbank_uid → figi → isin → broker_code → ticker → name`.

- совпал идентификатор → найден; новые идентификаторы строки дописываются к нему (`origin = import`);
- идентификаторы указывают на РАЗНЫЕ инструменты (тикер → A, ISIN → B) → строка с ошибкой, ничего не склеивается;
- совпало только название — и то лишь при совместимых типе и валюте;
- ничего не нашлось → новый инструмент, `id` = нормализованный код (не `TMON@`); занятый `id` — ошибка
  резолва, а не молчаливая привязка к чужому инструменту (раньше `onConflictDoNothing`);
- название, учившееся на другой строке файла, где тикер/ISIN уже резолвится, подхватывается заранее —
  порядок строк не влияет (случай LKOH).

**Политика неоднозначности.** Автоматически связывается только то, что совпало по идентификатору.
Эвристическое сходство (общий хвост кода `TCS00A10B4K3` ↔ `RU000A10B4K3`, близкое название, тикеры,
совпавшие после нормализации) только **подсказывает**: строка получает `warn` с «возможно, это …», а в
справочнике есть список «Возможные дубли». Связь появляется лишь по решению пользователя. Эвристики —
отдельные чистые функции (OCP), на автоматический резолв не влияют.

**Как пользователь разрешает неопознанный инструмент** (единственный, кто пишет в таблицу, —
`InstrumentIdentityService`):

1. В предпросмотре импорта (до появления дубля): «новый» или «это существующий: [подсказки сверху]».
   Выбор записывается с `origin = manual` при подтверждении импорта.
2. После факта — «Слить»: в **одной транзакции** переносит операции, историю цен (при одной валюте),
   вариационную маржу и ВСЕ идентификаторы источника на цель (`origin = merge`), затем удаляет источник.
   Повторный импорт после удаления сделок резолвится в цель — дубль не возвращается.
3. Синк Т-Банка без предпросмотра: новый инструмент создаётся (синк не блокируем), дубли ловит список
   «Возможные дубли».

Удаление сделок/систем/портфелей справочник и идентификаторы **не трогает**: это знание, а не данные
операций. Идентификаторы удаляются вместе с инструментом (cascade); слияние сначала переносит их.
Очистка неиспользуемых инструментов в проект не входит; если появится — обязана предупреждать, что
теряются выученные связи.

**Миграция существующих дублей** — `pnpm db:fix-duplicates` (dry-run) / `--apply`: детерминированные
(`TMON@` → `TMON`, тикер совпал после нормализации, тип и валюта те же) сливаются тем же кодом, что и
кнопка «Слить»; одиночный `X@` — правится только `ticker` (id не меняется), источник цены выбирает пользователь;
недетерминированные пары не трогаются. Резервная копия файла БД, одна транзакция, инварианты до/после
(число операций; по портфелю — позиции, вложено, реализованный P&L, доходы, кэш); расхождение → откат.

### 2.5. `trades` — закрытые/открытые сделки (вычисляется)

Это ваш лист «Закрытые сделки». **Не вводится руками** — собирается движком из
операций: покупки и продажи одного инструмента группируются в сделку.

| Поле | Описание |
|---|---|
| `id` (= Trade ID) | Идентификатор сделки |
| `instrument_id`, `system_id`, `portfolio_id` | Контекст |
| `status` | Открыта / Закрыта / Частично закрыта |
| `qty_bought`, `qty_sold` | Куплено / продано штук |
| `invested_ccy`, `invested_rub` | Вложено (с комиссией) |
| `dividends_rub`, `coupons_rub` | Дивиденды / купоны |
| `proceeds_ccy`, `proceeds_rub` | Выручка (по продажам) |
| `current_price`, `current_value` | Текущая цена/стоимость (из котировок) |
| `pnl_ccy`, `pnl_rub` | Финансовый результат |
| `opened_at`, `closed_at` | Даты |
| `direction` | `Long` / `Short`. У не-фьючерсов всегда `Long`; у фьючерса — по стороне открывающей части (Buy → Long, Sell → Short) |
| `opened_time`, `closed_time` | Время «ЧЧ:ММ:СС» из `executed_at` первой/последней операции; `null` у старых операций без времени |
| `fees_rub` | Комиссии всех операций сделки. Уже учтены в `pnl_rub`: у закрытой сделки gross = `pnl_rub` + `fees_rub` |

Сделка фьючерса открывается, когда позиция уходит из нуля (в любую сторону), и
закрывается, когда возвращается в ноль; переворот через ноль закрывает текущую сделку
и открывает новую на остаток (комиссия делится пропорционально количеству).

#### Статистика торговой системы (`systemPerformance`, `libs/core/performance.ts`)

Страница `/systems/:systemId` показывает статистику результатов любой системы —
фьючерсы и акции считаются одной и той же функцией, потому что различие инструментов
уже скрыто в движке, а метрики работают с результатом сделки в ₽. В DTO метрики разделены
по **базису** (у каждого блока он подписан в поле `basis`): `tradeMetrics` — только по
закрытым сделкам (win rate, profit factor, payoff, матожидание, серии, срок удержания);
`equityMetrics` — по дневной кривой «Результат системы» (просадка, recovery factor, Sharpe,
Sortino). Открытая позиция в метрики сделок не подмешивается. Деньги — `decimal.js`, наружу — decimal-строки; безразмерные
коэффициенты — `number`, `null` = «не определено».

| Метрика | Определение / допущения |
|---|---|
| Результат (net) | Σ `pnl_rub` закрытых сделок (после комиссий) |
| Gross | net + комиссии закрытых сделок |
| Комиссии, доля | Σ `fees_rub`; доля = комиссии закрытых / gross, % (`null`, если gross ≤ 0) |
| Открытые | `openRealized` (уже зафиксированное: комиссии входа, частичные закрытия) и `unrealized` (по расчётной цене) — отдельными полями; всего = net + openRealized + unrealized |
| Win rate | прибыльные / закрытые, %. Сделка «в ноль» — отдельный счётчик, победой не считается. Единая реализация `outcomeStats` (её же использует `tradeStats`) |
| Лонг / шорт | счётчик, win rate и net отдельно по `direction` |
| Средний выигрыш / убыток | Σ прибылей / число прибыльных; Σ убытков / число убыточных (≤ 0) |
| Payoff ratio | средний выигрыш / \|средний убыток\| |
| Profit factor | Σ прибылей / Σ убытков (по модулю); `null`, если убытков не было |
| Матожидание | net / число закрытых сделок, ₽ на сделку |
| Крайние сделки | наибольший выигрыш и наибольший убыток |
| Серии | макс. подряд прибыльных / убыточных; безубыточная сделка серию обрывает; «текущая» — серия на последней сделке |
| Кривая по закрытым сделкам | накопленный net по **дате закрытия**, точка на сделку-день; стартовая точка = 0 в день открытия первой сделки (или за день до первого закрытия). Отвечает на вопрос «качество входов и выходов» |
| Кривая «Результат системы» | дневной ряд `valuationSeries` по системе: зафиксированное + переоценка остатка по цене дня (см. «Две кривые системы» ниже). Отвечает на вопрос «как реально менялись деньги системы» |
| Макс. просадка | наибольшее падение **дневной кривой результата** от пика до дна, ₽ (`absoluteDrawdown`), включая бумажные потери по открытым позициям. Это отдельная функция: `metrics.maxDrawdown` работает с рядом **стоимости** (относительная, пик > 0) |
| Длительность просадки | дней от пика до восстановления (или до последней точки, если не восстановилась); дата восстановления — первая точка после дна, где кривая ≥ пика |
| Recovery factor | (результат на конец кривой − на начало) / макс. просадка; `null`, если просадки не было |
| Срок удержания | в часах, если у обоих концов сделки есть время (`hasTime`), иначе по датам (дни × 24). Средний, у прибыльных, у убыточных |
| Sharpe | среднее дневного изменения кривой результата / выборочное σ × √252 |
| Sortino | среднее дневного изменения кривой / нижнее отклонение от 0 × √252 |
| Разрезы | P&L по месяцам и дням недели (по дате закрытия), гистограмма результатов (число интервалов по Стёрджессу, ≤ 12) |

Sharpe/Sortino на странице показываются от 20 дневных значений (меньше — шум). Период `till` в прошлом: нереализованный результат не считается (котировки только текущие). Допущения Sharpe/Sortino: капитала у системы в модели нет, поэтому считаются по дневному
результату в ₽ (отношение среднего к разбросу не зависит от масштаба), безрисковая ставка
= 0. Дни — все будни дневной кривой (дни без изменения = 0) плюс выходные, в которые
результат менялся. Метрики в % от капитала (доходность, CAGR, просадка %)
не строятся: нужно поле «капитал системы» (см. открытые вопросы в отчёте задачи).

#### Аннотации исполнения (`operation_annotations`, необязательно)

Тег причины входа/выхода и сигнальная цена — аннотации 1:1 к уже импортированным
операциям (не второй журнал сделок). Таблица: `operation_id` (PK, FK ON DELETE CASCADE),
`tag`, `signal_price` (₽ за контракт, строкой), `source` (id парсера), `imported_at`.
Источник — CSV терминала (парсер `quik-trades`, интерфейс `AnnotationParser`): строка
сопоставляется с операцией по **номеру сделки** (`trade_num` = `brokerRef`) и проходит
проверку согласованности (инструмент, сторона, количество, цена, дата); несопоставленные
строки показываются с причиной. Код контракта терминала переводится в тикер отчёта
через `FUTURES_SPECS[серия].quikCode` (`CRZ6` → `CNY-12.26`). Цены выгрузки переводятся в
₽ за контракт сдвигом запятой (`scaleByPowerOfTen`). **Комиссии выгрузки игнорируются** —
это оценка терминала (19,54 ₽ против 7,40 ₽ фактических по той же сделке); факт — в
отчёте брокера. Проскальзывание считается в ядре: Buy — (цена − сигнал) × кол-во,
Sell — (сигнал − цена) × кол-во; плюс = потеряли. Блок «Исполнение» страницы системы
появляется только при наличии аннотаций.

#### Факты и производное: история цен и дневные ряды

Хранятся **только факты**: журнал операций и история цен (`price_history`). Всё производное —
чистая функция: из журнала и цен `valuationSeries` (`libs/core/valuation.ts`) считает дневной
ряд, из которого строятся **все** графики динамики (стоимость портфеля, стоимость
инструментов, кривая системы). Готовые ряды в БД не сохраняются: правка операции задним числом
меняет только дни ≥ её даты просто потому, что ряд считается заново — инвалидировать нечего.
Поэтому таблицы снимков портфеля (`portfolio_snapshots`, `snapshot_positions`,
`snapshot_invalidations`) удалены, а их содержимое перенесено в `price_history`
(`source = 'snapshot'`, цена за штуку = стоимость / количество).

**`price_history`** — цена инструмента на дату, PK (`instrument_id`, `date`):
`price`, `currency` (валюта ЦЕНЫ — как в `quotes`, у замещающих облигаций это валюта
номинала), `accrued_interest` + `accrued_currency` (НКД облигаций; валюта НКД своя),
`source` ∈ moex | cbr | binance | broker-report | quote | snapshot | manual. Курсы валют лежат в той же
таблице под синтетическим id `fx:USD` (₽ за единицу, валюта цены RUB): один механизм
догрузки, хранения и чтения, без отдельной таблицы и без FK на `instruments`.

Приоритет источников при конфликте на одну дату — **одно место** (`PRICE_SOURCE_PRIORITY`,
`libs/core/price-history.ts`): рынок (moex/cbr/binance) > отчёт брокера > `quote` (цена момента
«Обновить цены»: внутридневная, не официальное закрытие; официальное значение её заменяет и
покрытием не считается) > снимок > ручная.
Равный приоритет — побеждает свежая запись. Запись во все стороны идёт через `recordPrice`.

Заполнение — по требованию: `PriceHistoryService.ensure()` догружает только недостающие
хвосты диапазона (покрытие считается по рыночным точкам; снимок и ручная цена диапазон не
закрывают) через узкий интерфейс `PriceHistoryProvider` (ISP): MOEX ISS history (акции/ETF,
облигации с НКД на дату, валюта SELT, фьючерсы с расчётной ценой × множитель), история
курсов ЦБ, дневные свечи Binance. Сбой источника не роняет расчёт: день остаётся «без цены»
и помечается в ряду; повторная попытка — не чаще раза в час. Кроме того, «Обновить цены»
пишет цену дня и курсы в историю, а расчётные цены фьючерсов из отчёта брокера — с
`source = 'broker-report'`.

**`valuationSeries`** — точка на день по группе (`portfolio` | `system` | `instrument`):
`fixedRub` (зафиксированное нарастающим итогом: продажи, в т.ч. частичные; выплаты на дату
выплаты; комиссии фьючерсов — события `TradeLedger`; отдельные налоги и комиссии `Tax`/`Fee` — со знаком «минус»), `investedRub` (себестоимость остатка),
`marketValueRub` (рыночная стоимость; у фьючерса — нереализованный результат),
`unrealizedRub` = стоимость − вложено, `totalRub` = зафиксированное + переоценка. Позиции
ведёт тот же `TradeLedger`, что и `calculateTrades`, оценка — тот же `marketValueRub` (НКД,
валюта цены и валюта НКД) и `futureUnrealizedPnl`: поэтому точка «сегодня» совпадает с итогом
по сделкам, а не «похожа» на него. Цена дня — последняя известная ≤ дня (forward-fill). Нет
цены или курса — остаток по себестоимости (переоценка 0) и пометка `carried` у точки
(`no-price` / `no-fx`); перенос цены дольше трёх суток — `carried` (выходные и праздничные выходные не помечаются).

**Две кривые системы** — две разные величины, а не одна с новым смыслом:

| | Кривая по закрытым сделкам | «Результат системы» |
|---|---|---|
| Вопрос | качество входов и выходов | как реально менялись деньги системы |
| Точки | по одной на закрытую сделку | каждый день |
| Состав | только закрытые сделки | зафиксированное (все продажи, в т.ч. частичные; дивиденды и купоны по дате выплаты; минус комиссии) + переоценка остатка по цене дня |
| Метрики | win rate, profit factor, payoff, матожидание, серии | просадка, Sharpe, Sortino, recovery factor |

Выплата, зачисленная после продажи бумаги, относится к последней закрытой сделке позиции.
Дивиденды/купоны без инструмента (операция без `instrument_id`) к сделке не относятся, но
деньги получены: в дневной ряд они входят отдельным потоком по дате выплаты (в группировке по
инструментам — группа «Без инструмента»), в итог системы — как выплата по закрытым. Лучше всё
равно привязать такую операцию к бумаге.

#### Доходность за период: единый расчёт (`periodPerformance`, `libs/core/period-performance.ts`)

Все цифры доходности за период — карточки дашборда, линия «Портфель» в «Портфель против рынка»,
просадка, «P&L по системам», таблица эффективности — берутся из **одной** чистой функции поверх
дневного ряда `valuationSeries` и отдаются одним DTO: `GET /api/performance?scope=all|portfolio|system&id&portfolioId&from&till`
(`PerformanceSchema` в `schemas.ts`). Фронт ничего не пересчитывает, только рисует. Прежние `ROI`
(«P&L / себестоимость текущих позиций»), `periodCashFlows` и `timeWeightedIndex` удалены: у них была
несопоставимая база и второй независимый расчёт.

```
operations + price_history ─► valuationSeries ─► periodPerformance(контур, from)
                                                       │
                              GET /api/performance ◄───┘  → карточки · график против рынка · таблица
```

**Контур** — что считаем капиталом и что внешним потоком. Для каждого дня есть капитал V_t и поток
F_t (+ = деньги внутрь):

| Контур | V_t (капитал) | F_t (внешний поток) |
|---|---|---|
| `wealth`: весь журнал или один счёт (у него есть свой кэш) | богатство = позиции + кэш = чистый ввод + итог | Deposit − Withdraw |
| `positions`: система или инструмент (своего кэша нет) | рыночная стоимость позиций группы | покупки − выручка продаж − выплаты |

Оба случая — одно тождество. Накопленный итог P_t = зафиксированное + переоценка (`totalRub`), по
определению результата ΔV = ΔP + F, откуда `F_t = (V_t − P_t) − (V_{t−1} − P_{t−1})`. Поэтому поток не
собирается из операций отдельно и не может разойтись с рядом.

**Три метрики** (из пары рядов V, F — одинаковыми формулами для любого контура):

| Метрика | Определение | Отвечает на вопрос |
|---|---|---|
| **Результат, ₽** | `V_end − V_start − ΣF` = Δ зафиксированного + Δ переоценки; разбивка: реализованное / выплаты / переоценка **за период** | сколько заработано за период |
| **Доходность стратегии (TWR), %** | цепочка дневных доходностей `r = (V_t − V_{t−1} − F_t) / (V_{t−1} + max(F_t, 0))`; ряд индекса и итог карточки — один массив, последняя точка = карточка | насколько хорошо работал капитал независимо от того, когда вносили деньги; сравнима с индексом рынка |
| **Доходность ваших денег** | период ≥ 365 дн. — **XIRR** в годовых; короче — **Modified Dietz** (результат / средний капитал) за период | сколько дали именно ваши деньги с учётом сумм и дат вводов |

- **База периода — рынок, а не себестоимость.** V_start — стоимость на последний день ДО `from`
  (оценка по цене дня); прибыль, заработанная до периода, в результат периода не входит. Без точки до
  `from` (период с первой операции) база нулевая, а ввод первого дня — весь стартовый капитал.
- **Соглашения TWR:** ввод работает с **начала** дня (входит в базу — на него покупают и платят
  комиссии), вывод снимается в **конце** дня. Так вклад 2 млн ₽ после остатка 1 198 ₽ не даёт
  ложной просадки −81%. При V_{t−1} < 0 или нулевой базе день считается нулевым (делить не на что).
  Ряд индекса начинается с точки базы 100 (день до периода), поэтому доходность первого дня входит.
- **Депозит до первой сделки.** Ряд `valuationSeries` начинается с первой СДЕЛКИ (или выплаты), а не с первого
  ввода: деньги, внесённые раньше, входят в чистый ввод первой точки, и для периода «с первой операции» их вес
  в Dietz и XIRR считается с этого дня, а не с даты Deposit. Это допущение: простой кэша до первой покупки в
  доходность не входит (иначе месяцы без сделок «разбавляли» бы результат).
- **TWR и XIRR датируют поток по-разному.** TWR считает ввод с начала дня потока, XIRR — на дату потока; расхождение
  в день на итог влияет слабо.
- **Налоги и комиссии в контуре позиций.** У системы нет кэша, поэтому её `Tax`/`Fee` уменьшают результат, а
  капитал (стоимость позиций) не меняется — по тождеству F = Δ(V − P) это выглядит как «довнесённые» деньги на
  покрытие издержек. Для контура счёта (`wealth`) издержки просто уменьшают богатство.
- **Средний капитал (Dietz):** `V_start + Σ w·F`, вес — доля периода, в течение которой поток работал
  (ввод — с начала дня, вывод — с конца).
- **Нет капитала → процентов нет.** Система только из фьючерсов (вложено 0, «стоимость» — это
  переоценка) показывает рубли, а проценты — «нет капитала за период».
- **Капитал в минус → процентов нет.** Если капитал контура уходил ниже нуля (покупки без внесённых денег:
  не хватает Deposit или перевода), TWR, Dietz и XIRR недостоверны — TWR пропускает такие дни, а Dietz и XIRR
  считают их иначе, и цифры расходились втрое. Тогда проценты не показываются (причина `negative-capital`), а
  результат в ₽ верен; причину объясняет предупреждение о кэше.
- **Короткий период не аннуализируем:** XIRR на окне короче года — статистический шум; карточка
  меняет подпись («за период» / «% годовых»), правило — `ANNUALIZE_FROM_DAYS` в core, а не в шаблоне.
- Деньги — `Decimal` по всему расчёту, наружу decimal-строки; коэффициенты (%, индекс) — `number`.

**Почему TWR ≠ XIRR — это не баг.** TWR не знает, сколько денег и когда вы вносили, XIRR знает.
Пример (фикстура `midDepositBeforeFlat`): капитал 100 000 вырос на 10%, затем довнесено ещё 100 000, и вторая
половина года — без роста. TWR = **10%** (стратегия сработала на +10%), доходность ваших денег ≈ **6,7%**
(больше половины денег работали во флэте). Карточки обязаны иногда расходиться: расхождение показывает, как
повлияло время вводов.

**Перевод денег между счетами** (`Transfer` без инструмента) для счёта — внешний поток, как Deposit/Withdraw: знак
несёт сумма (входящий — плюс, исходящий — минус, как в `cashBalanceRub`); на весь журнал пара переводов гасится.
Без этого кэш счёта с переводом расходился с журналом, а доходность первого дня считалась от нулевого капитала.
Перевод ценных бумаг (`Transfer` с инструментом) в ряд не входит — позиции его не двигают; бумага, пришедшая
переводом, не видна ни в ряду, ни в проверке купонов (известное ограничение).

**Отдельные налоги и комиссии входят в итог.** Операции `Tax` и `Fee` без привязки к сделке (движок не
разносит их по сделкам) идут в `fixedRub` своей группы со знаком «минус» (`isStandaloneCost`); по фьючерсам их
пропускаем — комиссии уже в реализованном результате. Без этого богатство завышено на удержанные налоги, а
**кэш из ряда ≠ `cashBalanceRub`**: инвариант «кэш ряда на любую дату = кэш журнала» закреплён тестом
(`cashSeries` в `valuation-extras.ts`, `valuation-extras.spec.ts`).

**График «Стоимость инструментов во времени».** Стек позиций по инструментам плюс верхний слой
«Деньги» (`cashSeries` = богатство − позиции); вершина стека = богатство и не падает при продаже: стоимость
переливается из слоя бумаги в «Деньги», выплата добавляет в «Деньги». Маркеры событий — выплата ▲ и продажа ◆
(`valuationEvents`; сумма и бумага в подсказке). Слой «Деньги» есть только у контура со своим кэшем (`hasCash`
в ответе `/api/valuation/series`: без фильтра по системе); у системы/инструмента деньги от продаж и выплат уходят
в общий кэш счёта — подпись под графиком.

**Ориентир («Портфель против рынка»).** Сравнивается TWR портфеля (обе величины очищены от ваших потоков) с
индексом на базе 100 в первый день периода (`libs/core/benchmark.ts`, `GET /api/benchmark`; запрос валидируется
`BenchmarkQuerySchema`: реальные календарные даты, окно до 20 лет, SECID из whitelist). Ряды индексов
хранятся в `price_history` под id `index:SECID` (валюта `IDX`) и догружаются тем же `PriceHistoryService.ensure`,
что и цены бумаг — отдельного пути за историей индекса нет:

| Ориентир | Что это | Замечание |
|---|---|---|
| `MCFTRR` (по умолчанию) | индекс МосБиржи полной доходности, **нетто** | дивиденды журнала приходят «налог удержан» — честное сравнение с нетто-индексом |
| `RGBITR` / `RUCBTRNS` | ОФЗ / корпоративные облигации, полная доходность | для облигационной части |
| `IMOEX` | ценовой индекс | без дивидендов; остаётся выбираемым с пометкой — занижает рынок |
| `RUSFAR` (линия «Денежный рынок») | ставка денежного рынка, % годовых | не индекс: уровень растёт на ставку дня / 365 по фактическим ставкам; заменила константу 16% |

**Полнота журнала** (`journalCompleteness`, `libs/core/journal-completeness.ts`). Невидимые пропуски журнала
тихо портят доходность, поэтому дашборд показывает «Данные: N предупреждений» (рядом с пометками цен `carried`), а
карточки периода, который задевает предупреждение, помечаются; метрики не блокируются.

| Проверка | Условие |
|---|---|
| Пропущенный купон | по графику ISS (`bondization`) бумага удерживалась и на дату фиксации реестра, и за 2 дня до неё (проданное накануне реестра купон не получает; без даты фиксации реестр ≈ за 3 дня до выплаты), а операции «Купон» в окне −3…+10 дней от выплаты нет; Coupon без инструмента закрывает одну выплату |
| Отрицательный кэш | вычисленный кэш (богатство − позиции) ушёл ниже −1 ₽: не хватает Deposit/перевода — довнесение выглядит как прибыль |

Пороги — константа `COMPLETENESS` (одно место). График купонов кэшируется в БД (таблицы `coupon_schedule` и
`coupon_schedule_loads`, миграция 0020; отдельно от `price_history`, потому что это расписание событий со своей
формой и сроком годности) и перезагружается, когда старше 7 дней или не покрывает начало периода — «сегодня» на
свежесть не влияет (проверяются только купоны, чьё окно ожидания 10 дней уже закрылось, они старше загруженной
границы). Пустой ответ ISS без блока купонов — ошибка источника, кэш не стирается; сбой сети не роняет расчёт.
Все запросы к внешним источникам идут с таймаутом 10 с (`fetchWithTimeout`). **Проверка дивидендов по
расписанию не делается:** эндпоинт ISS `/iss/securities/{SECID}/dividends.json` не отдаёт блок дивидендов (проверено
на SBER, X5, LKOH) — источник не придумываем.

## 3. Типы операций (enum `operation_type`)

Собрано из ваших данных — движок должен уметь распознавать все эти виды:

| Тип | Что делает с позицией | Пример из ваших данных |
|---|---|---|
| `Deposit` | Ввод кэша на счёт | Deposit RUB 497 782 |
| `Withdraw` | Вывод кэша | Withdraw RUB 505 799 |
| `Buy` | Покупка → открывает/увеличивает позицию | Buy SBER 1600 |
| `Sell` | Продажа → уменьшает/закрывает позицию | Sell SBER 1600 |
| `Dividend` | Дивиденд → в `dividends_rub` | LKOH 31 733 |
| `Coupon` | Купон по облигации → в `coupons_rub` | RU000A10B4K3 21 462 |
| `Tax` | Налог → уменьшает результат | Tax RUB 1 198 |
| `Fee` | Отдельная комиссия | — |
| `Transfer` | Перевод между портфелями (парой строк) | Между портфелями = Да |

**Перевод между портфелями** — важный кейс: это две связанные операции (списание из
портфеля А + зачисление в портфель Б), объединённые `transfer_group`. Движок не
должен считать это покупкой/продажей и не должен искажать P&L.

## 4. Движок расчётов (что программа считает сама)

Логика, которую вы сейчас держите в формулах Google Sheets, переносится в код и
покрывается тестами.

**Метод учёта:** по умолчанию **средневзвешенная цена** (как у вас сейчас — «Средняя
цена покупки»). Опционально можно добавить FIFO — это влияет на расчёт налога и
реализованного P&L. Метод задаётся в настройках.

Что пересчитывается при любом изменении журнала:

1. **Средняя цена покупки** позиции считается **по оставшимся (не проданным) лотам**,
   а не по всем историческим покупкам. Важно: в ваших текущих данных «Средняя цена»
   и «Вложено» не всегда связаны как `вложено = кол-во × средняя` — например, у SBER
   (400 шт, средняя 303.51) «Вложено» 76 742.95 — это **нетто после частичной
   продажи** 240 шт, а не 400 × 303.51. Движок должен различать: средняя цена — по
   методу учёта (средневзвешенная/FIFO) на остаток; «Вложено» — фактически вложенный
   капитал с учётом реализованных частей. Оба показателя тестируются на ваших цифрах.
2. **Вложено** (в валюте и в RUB, с комиссией) — с корректной обработкой частичных
   продаж.
3. **Реализованный P&L** — при продажах (выручка − себестоимость проданной части).
4. **Нереализованный P&L** — по текущей котировке (текущая стоимость − вложено).
5. **Дивиденды/купоны** — накапливаются в позицию и в сделку.
6. **Пересчёт в RUB** — по `fx_rate` на дату операции (исторический) и по текущему
   курсу (для текущей стоимости).
7. **Статус сделки** — открыта / частично / закрыта по остатку количества.
8. **Сводка по системе и по портфелю** — агрегаты для дашборда.

### Фьючерсы (тип `Future`)

Источник один — отчёт брокера (HTML, таблица «Срочные сделки»). Моста QUIK и отдельных
срезов стратегий нет: фьючерс живёт в той же таблице `operations`, что и всё остальное.

- **Тикер** — как в отчёте: `CNY-12.26`. Название содержит дату исполнения.
- **Цена за контракт.** Цена в отчёте умножается на множитель серии (справочник
  `FUTURES_SPECS` в `libs/core/src/lib/futures.ts`, `CNY` → 1000) сдвигом запятой по
  строке, не через `number`: 12,467 → 12 467 ₽. Количество — в контрактах. Неизвестная
  серия или опцион — строка с ошибкой и причиной, в журнал не пишется.
- **Позиция со знаком:** лонг > 0, шорт < 0, средняя цена входа по открытой части.
  Переворот через ноль = закрытие + новая позиция по цене сделки.
- **Результат считается по цене сделок (способ А):** при закрытии/уменьшении
  `(цена закрытия − средняя) × кол-во × знак`; нереализованный —
  `(расчётная − средняя) × кол-во со знаком`. Вариационная маржа из «Движения денежных
  средств» намеренно пропускается, иначе двойной учёт.
- **Комиссия** (брокер + биржа) вычитается из реализованного результата в момент каждой
  сделки — ровно один раз, видна у открытой позиции.
- **«Вложено» = 0.** В стоимость идёт только нереализованный результат.
- **Деньги:** сделки фьючерса не двигают кэш «купил — заплатил»; кэш меняется на
  изменение реализованного результата (уже за вычетом комиссий).
- **Расчётная цена** берётся из «Срочного рынка» отчёта и при подтверждении импорта
  сохраняется как цена инструмента на дату конца периода (`quotes`, источник `manual`,
  RUB); более свежую цену старый отчёт не затирает.
- **Проценты доходности** (TWR, доходность денег) у системы только из фьючерсов не считаются:
  вложено 0, «стоимость» — это переоценка, делить на капитал нечего («нет капитала за период»).
  Результат в ₽ есть всегда; в портфельном контуре он входит в богатство через кэш.
- **Дедуп** — по номеру сделки (`broker_ref`): повторная загрузка и пересекающиеся
  периоды дублей не создают.
- **Эталон на реальном отчёте** SESPS 27.10–05.11.2026 (14 сделок, позиция −128,
  расчётная 12 387): результат по цене сделок + нереализованный = −10 913 ₽ = вариационной
  марже отчёта (204,00 − 11 117,00); комиссии 962,91 ₽ учитываются отдельно.

> Ключевое: вы вводите операцию → всё остальное (позиции, сделки, итоги)
> пересчитывается автоматически. Ручного дублирования нет.

## 5. Мультивалютность (RUB / USD / крипто)

В ваших данных есть RUB, USD (облигация `RU000A10B4K3`, крипта). Правила:

- У каждой операции — **валюта сделки** и **курс к RUB на дату** (исторический,
  фиксируется в момент операции — не пересчитывается задним числом).
- Текущая стоимость считается **и в валюте инструмента, и в RUB** по **текущему**
  курсу из `quotes`.
- Итоги портфеля показываются в RUB (базовая валюта отчётности), с возможностью
  переключить на валюту инструмента.

### Целостность денег при импорте: пять принципов

Выведены из разбора реальных расхождений кэша с брокером (T-Invest API, сверка с `GetPositions`).

- **П1. Одно списание брокера — одна запись.** Комиссию сделки API присылает дважды: полем
  `commission` и дочерней `BROKER_FEE`; суммы совпадают (76 из 76 случаев). Берём сумму
  дочерних `BROKER_FEE`, если они есть, иначе `commission`; **никогда не складываем**.
- **П2. Знак суммы задаёт брокер.** `payment` приходит со знаком, тип определяет только категорию:
  расходные (`tax`, `fee`, `withdraw`) пишутся как `−payment`, доходные (`deposit`, `dividend`,
  `coupon`) и перевод — как `+payment`. Отрицательная сумма — возврат или сторно (`Tax` с минусом,
  `Fee` с минусом, `Dividend` с минусом). Неизвестный тип операции **не угадывается** (раньше был
  `Buy`): строка получает ошибку предпросмотра, и ничего молча не попадает в журнал.
  - **Дивиденд «на карту»** (`DIV_EXT`): брокерский счёт он не затрагивает, налог по нему со счёта тоже
    не списывается. Пишутся `Dividend` (брутто) и `Withdraw` (брутто − налог) с общим
    `transferGroup`; налог остаётся обычной `Tax`; три записи в кэше дают ноль.
- **П3. Кэш только рублёвый; валюта на счёте — позиция.** Валютное пополнение разворачивается при
  импорте в `Deposit` (та же сумма и валюта, заполненный `fxRate`) + `Buy` валютной пары на то же
  количество по тому же курсу (`brokerRef = {id}:fx`, общий `transferGroup`). Вывод валюты — зеркально.
  Курс: если в тот же день есть продажа этой валюты (в загрузке или журнале) — её средневзвешенная
  цена (деньги прошли транзитом, курсовой разницы нет), иначе курс ЦБ на дату. Для прочих нерублёвых
  строк `fxRate` обязателен; нет курса — ошибка предпросмотра, а не молчаливая единица.
- **П4. Один расчёт кэша.** `cashDelta` (`cash.ts`) — единственное место со знаком операции;
  `dailyCash` — нарастающий итог по дням (фьючерсы — реализованным результатом); `cashBalanceRub` и
  `cashSeries` — обёртки над ним. Инвариант: чистый ввод + итог − стоимость = кэш − продажи без
  позиции (`orphanSellsRub`). Продажа без позиции не маскируется и не считается доходом: она
  становится причиной в предупреждении о полноте журнала.
- **П5. Время операции.** Парсер API передаёт время (МСК) для всех строк; порядок внутри дня зависит
  от него. Время сделки также обновляется повторным импортом.

**Известное ограничение — НКД облигаций.** Цена сделки в журнале — без накопленного купонного дохода,
а брокер списывает/зачисляет его деньгами. Поэтому кэш журнала выше остатка у брокера на чистый
уплаченный НКД (на реальных данных ≈ 17 841 ₽ по 25 сделкам с облигациями). Сверка с `GetPositions`
сходится до копеек, если эту разность учесть.

## 6. Дедупликация при импорте

Чтобы повторная загрузка отчёта не задвоила операции:

- Каждая операция получает `broker_ref` (номер операции у брокера) — если он есть.
- При отсутствии реф-номера — хэш из (дата + тикер + тип + количество + сумма).
- Импорт помечается `import_batch_id`, любую загрузку можно откатить целиком.

### Повторный импорт обновляет, а не только пропускает

Источник сделок любой (HTML-отчёт, API брокера), итог один — журнал операций. Если у
уже импортированной операции (тот же `broker_ref` и портфель) брокер прислал другие
значения — например, комиссия пришла позже, — предпросмотр показывает статус **«update»**
с диффом «было → станет», а подтверждение **обновляет существующую операцию**, не
создавая дубль. Единая политика приоритета — `mergeBrokerFields` (`libs/core/import.ts`):

- отчёт/API брокера авторитетны для денег и количества; обновляются `fee`, `price`,
  `quantity`, `executed_at`. Нулевая комиссия известную не затирает; пустое время
  существующее не стирает;
- система, заметки и прочая разметка пользователя **не трогаются**;
- аннотации (CSV терминала) не меняют ни одного поля операции;
- обновление ничего не инвалидирует: ряды динамики считаются из журнала заново. Откат
  загрузки удаляет операции батча, но не возвращает старые значения обновлённых
  (интерфейс об этом предупреждает).

**Комиссия отдельной строкой.** Общий шаг нормализации `attachParentFees`: строка с
`RawRow.parentBrokerRef` (так API Т-Банка присылает `OPERATION_TYPE_BROKER_FEE` с
`parentOperationId`) прибавляется к `fee` родителя с таким `brokerRef` внутри той же
загрузки и исчезает из списка. Сумма пересчитывается из загрузки (родитель + дети), а не
прибавляется к значению из базы, поэтому повторный импорт идемпотентен. Родителя в
загрузке нет — строка остаётся обычной комиссией. Парсер Т-Банка этим полем не пользуется: у его строк-сделок `brokerRef` — номер
биржевой сделки, а `parentOperationId` указывает на id операции, поэтому
`OPERATION_TYPE_BROKER_FEE` с родителем-сделкой сворачивается в комиссию родителя
прямо в парсере (распределяясь по исполнениям). Фьючерсы T-Invest — отдельная задача.

### Сверка с вариационной маржой (фьючерсы)

Вариационная маржа (ВМ) из отчёта в P&L и в операции **не попадает** (способ А, иначе
двойной счёт). Парсер отдаёт её отдельным результатом (`settlements`), хранится в
`futures_settlements` (портфель × инструмент × дата конца периода, upsert) и используется
только для контроля качества данных. `reconcileFuturesSettlement`: результат движка за
период отчёта = [реализ. gross(≤конец) + нереализ.(по расчётной на конец)] − [реализ.
gross(<начало) + нереализ.(по расчётной на начало)] против «ВМ за период + плановая ВМ».
Расхождение > 1 ₽ — предупреждение с суммой. ВМ привязана к счёту и инструменту, а не к
системе, поэтому индикатор показывается у позиции на странице «Портфель», а на странице
системы — только если весь инструмент в портфеле принадлежит этой системе.
