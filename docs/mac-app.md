# Приложение macOS и выпуск DMG

Приложение для Apple Silicon, минимальная macOS 13.0. Swift/AppKit и
`SMAppService.mainApp` (macOS 13+); у вложенного Node 22.22.3 и SQLite
13.0.1 `LC_BUILD_VERSION minos 11.0`. Минимум проверяется по бинарникам;
приёмка на самой macOS 13 остаётся отдельной проверкой на соответствующем Mac.
Источники требований: [Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice),
[Node 22.22.3 BUILDING.md](https://github.com/nodejs/node/blob/v22.22.3/BUILDING.md).

## Один выпуск

```sh
pnpm install --frozen-lockfile
pnpm release:mac 0.2.0 --build 1
```

Команда **каждый раз** очищает `dist/apps/api` и `dist/apps/web`, собирает оба
проекта с `--skip-nx-cache`, заново копирует миграции, автономный Node, зависимости,
SQLite и интерфейс. Затем компилирует Swift для arm64/macOS 13, подписывает
вложенные Mach-O и приложение, проверяет подписи и реальный SELECT через
подписанный Node, создаёт сжатый read-only DMG с приложением и ссылкой Applications.
Старые файлы в `dist` не подмешиваются. Внешний начальный Node и pnpm нужны только
на машине сборки. У пользователя не нужны Node, pnpm, Homebrew или репозиторий.

Выход: `dist/releases/0.2.0-1/Investment Portfolio.app`,
`dist/releases/0.2.0-1/Investment-Portfolio-0.2.0-arm64.dmg` и `release.json`
с SHA-256 образа, сервера и web. Версия и номер сборки находятся в Info.plist,
меню, «О программе» и build-manifest.json. `--local-test` явно маркирует
тестовый выпуск в меню и инструкции внутри DMG.

Имя `.app`, bundle ID `com.krisfeminova.investment-portfolio` и профиль
`~/Library/Application Support/Investment Portfolio` стабильны между версиями.
Профиль, `.env`, runtime прежней версии и пары восстановления не входят в DMG.

Перед каждым следующим выпуском: добавить изменения отдельными новыми миграциями
(уже применённые SQL не редактировать), обновить список изменений для пользователя,
выполнить выпуск, затем проверку с **фактическим DMG предыдущего релиза**:

```sh
pnpm test:mac:update \
  --previous /absolute/path/Investment-Portfolio-0.1.0-arm64.dmg \
  --next /absolute/path/Investment-Portfolio-0.2.0-arm64.dmg \
  --legacy-backup /absolute/path/anonymous-historical.sqlite
```

Для первого выпуска вместо прежнего публичного релиза используются две
явно тестовые версии:

```sh
pnpm release:mac 0.1.0 --build 1 --local-test
pnpm release:mac 0.1.1 --build 2 --local-test
pnpm test:mac:update \
  --previous dist/releases/0.1.0-1/Investment-Portfolio-0.1.0-arm64.dmg \
  --next dist/releases/0.1.1-2/Investment-Portfolio-0.1.1-arm64.dmg \
  --first-release --legacy-backup /absolute/path/anonymous-historical.sqlite
```

Без `--first-release` тест требует канал `release` у предыдущего образа,
чтобы тестовый образ случайно не подменил настоящий релиз. Происхождение и SHA
обоих входных образов записываются в отчёт. Тест ничего не пересобирает внутри
двух предоставленных DMG: монтирует read-only, копирует `.app`, запускает реальное
меню через LaunchServices, создаёт записи через HTTP приложения, штатно завершает,
заменяет `.app` в том же каталоге, сравнивает данные и версию, добавляет запись
и повторяет запуск. Файловый адаптер приёмки вызывает те же действия Swift,
что кнопки меню; он включается только с `--test-profile` и `--test-control`.
Он не пишет SQLite, не подменяет health и не используется в обычном запуске.

Дополнительно тест создаёт **два дополнительных готовых fixture-DMG**, явно
помеченных `local-fixture`: один с новой синтетической SQL-миграцией, второй
с заведомо сломанной. Только эти тестовые артефакты получают синтетический SQL;
исходные миграции проекта и предоставленные релизные DMG остаются неизменными.
Проверяются автоматическая предмиграционная пара, сохранность исходной БД
при сбое и настоящий запуск прежнего сервера через действие восстановления.
Отчёт JSON сохраняется в `dist/mac-acceptance`, все профили и установки —
во временном каталоге, путь к нему включён в отчёт.

Историческая регрессия отдельно использует HTTP preview/restore сервера
**из нового готового DMG**, а затем его перезапуск. Для обезличивания старой
локальной базы с настоящей записью 0011 доступна команда:

```sh
node scripts/create-anonymous-legacy-backup.mjs /absolute/old.sqlite /absolute/new-anonymous.sqlite
```

Она открывает исходник только для чтения, получает согласованный SQLite-снимок
с WAL, удаляет все пользовательские строки из копии, заполняет только синтетический
счёт и две операции, выполняет `secure_delete` и `VACUUM`. История миграций
сохраняется без подмены хеша. Существующий файл назначения не перезаписывается.

## Поведение приложения

Первый запуск: пустой профиль, восстановление единственного SQLite-файла,
скачанного в разделе «Данные», или перенос из каталога проекта с учётом старой
`.env`. Выбранный путь и счётчики показываются до/после переноса. Отмена диалога
не запускает сервер и возвращает к мастеру. Токен T-Invest переносится отдельным
действием с подтверждением, через stdin, без других настроек и без записи токена
в лог. Используемый `.env` находится в профиле, права 0600.

Меню показывает «Остановлен», «Запускается», «Работает» или ошибку. Сервер
открывается браузером только после HTTP health с уникальным идентификатором
**своего** процесса. Чужой процесс на порту 3000 не останавливается. Повторные
нажатия не создают второй сервер; профиль дополнительно защищён SQLite-lock,
а меню — отдельной kernel flock. После закрытия вкладки сервер работает дальше.
«Остановить»/«Выйти» посылают SIGTERM собственному launcher, ждут завершения
HTTP, SQLite и дочернего Node. Принудительного уничтожения чужих PID нет.
После аварии меню launcher замечает смену ppid и завершает свой сервер; повторный
запуск открывает прежний профиль. Логи: `профиль/logs/app.log` (доступны из меню).

«Запускать при входе» использует `SMAppService.mainApp`. Меню отличает enabled,
notRegistered, requiresApproval и unavailable; системное разрешение открывается
в Login Items. После входа запускается меню и сервер существующего профиля,
при пустом профиле — мастер. Ручная остановка действует до следующего запуска
приложения/входа; регистрация автозапуска сохраняется. Для постоянного отключения
нужно снять «Запускать при входе». Настройка не меняется тестовым стендом.

## Обновление и возврат

Пользователь выбирает «Выйти», переносит новый `.app` из DMG в «Программы»
с заменой и запускает. Экспорт/импорт для обновления не нужны. Мастер появляется
только при отсутствии рабочей базы. Перед удалением старого `.app` его runtime
уже сохранён успешным предыдущим запуском в `.profile/releases`.

Перед новой схемой сервер создаёт согласованную пару «прежний runtime + БД»,
мигрирует отдельную копию и только после проверок публикует её. При сбое исходная
БД остаётся на месте. Для возврата остановить сервер и выбрать в меню
«Вернуться к версии до обновления…», выбрать `профиль/backups/update-…` и
подтвердить замену. Сначала создаётся страховочная пара текущего состояния;
затем запускается **сохранённый прежний runtime**. Его путь виден в «О программе».
Восстановленная база защищена от немедленной повторной миграции новой версией.
Низкоуровневые команды `prepare-update`, `recover-update`, формат пар и повторная
подготовка обновления описаны в [mac-runtime.md](mac-runtime.md).

## Подпись и публичный выпуск

Без Apple credentials команда делает **ad hoc** подпись с hardened runtime.
Только локальному Node добавлен `disable-library-validation`: у ad hoc нет Team ID,
иначе macOS отвергает `.node`. Developer ID использует отдельные entitlements
без этого исключения; Node и SQLite подписываются одним Developer ID.

```sh
MAC_SIGN_IDENTITY='Developer ID Application: Your Name (TEAMID)' \
MAC_NOTARY_PROFILE='portfolio-notary' \
pnpm release:mac 0.2.0 --build 1
```

`MAC_NOTARY_PROFILE` — заранее созданный профиль Keychain для `notarytool`;
секреты не передаются аргументами сборки. Порядок: вложенные Mach-O → `.app`
→ DMG → `notarytool submit --wait` → проверка Accepted → stapling `.app` и DMG
→ stapler validate → spctl. Ошибка любого шага прекращает выпуск; результат
нотарификации сохраняется. Основание:
[Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

Ad hoc не является Developer ID и не проходит Gatekeeper как публичная загрузка.
Подпись Developer ID, нотарификация, запуск скачанного quarantined DMG на чистом
Mac, macOS 13 и разрешение автозапуска требуют отдельной проверки с сертификатом
и соответствующей системой. Не следует выдавать локальное открытие образа за
успешный Gatekeeper-тест.

## Повторное открытие после отката

При открытии приложения и при команде меню «Запустить» Swift вызывает
`profile resolve-start` во встроенном runtime текущего .app. При отсутствии
отметки отката возвращается `launchPath: null`, выбирается встроенный сервер.
При откате команда проверяет путь сохранённого приложения внутри backups,
его идентификатор/полный отпечаток и совместимость с текущей схемой БД.
Готовность проверяется реальным запуском на согласованной временной копии
текущей БД, включая WAL. Затем возвращается путь сохранённого start.sh.

Это выбор сервера, а не повторный recover-update: снимок portfolio.sqlite
из пары не читается и не публикуется поверх текущего портфеля, страховочные пары
не создаются, отметка отката сохраняется. При повреждении сохранённого сервера
возвращается RECOVERY_APPLICATION_REQUIRED; автоматического повторного
восстановления снимка нет. Команды управления профилем всегда выполняются
встроенным runtime, HTTP может выполнять прежний сохранённый сервер.

Регрессия LocalProfile проверяет выбор сервера после отката даже при удалённом
файле снимка: новая запись в текущей БД и её SHA-256 сохраняются. Повреждённый
start.sh отклоняется. Тест готовых DMG дополнен записью операции после отката,
полным выходом меню, повторным открытием .app через LaunchServices и проверкой
той же операции, итога, пути сервера и отсутствия новых страховочных пар.
Дополнительно проверяется остановка/запуск меню и повторное открытие после
отката неудачного обновления.

## Канонические пути профиля — сборка 0.1.1 (4)

Исправлена ошибка сборки 3: `/var/...` и `/private/var/...` выбирали разные
`.profile/<hash>` для одной SQLite-базы. Теперь путь разрешается через realpath
существующего файла или ближайшего родителя ещё до открытия рабочей БД.
Под блокировками проверяются канонический и прежние хеши обоих написаний.
`required-release.json` и `pending.json` сравниваются с нормализацией путей.
Противоречия/повреждения дают `PROFILE_STATE_CONFLICT` до resume и миграций.
Пустой второй каталог не отменяет существующую отметку отката.

Состояния объединяются: сохранённые runtime переносятся в общее состояние,
старые каталоги сохраняются как `.legacy-*`, прежние имена становятся симлинками
на общее состояние. Это позволяет также прежнему серверу читать ту же отметку.
При разных current-release сохраняется канонический указатель (либо первый
