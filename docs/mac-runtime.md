Оболочка Swift, версия, выпуск `.app`/DMG и приёмка обновления задачи 3
описаны в [mac-app.md](mac-app.md). Ниже сохранены контракт runtime и история
проверок задач 1, 2А и 2Б.

Состояние на 14 ноября 2026: реализовано, без коммита на ветке
`feat/system-performance` поверх `da8d4e8`. Исходные незакоммиченные
`docs/tasks/mac-phone-*.md` не изменялись.

## Сборка

```sh
pnpm install --frozen-lockfile
pnpm build:mac
```

Хост сборки: macOS arm64, pnpm 9.15.9, начальный Node для запуска скрипта.
Дальше сборка использует скачанный Node 22.22.3 darwin-arm64. Источник:
официальный `https://nodejs.org/dist/v22.22.3/node-v22.22.3-darwin-arm64.tar.gz`.
SHA-256: `0da7ff74ef8611328c8212f17943368713a2ad953fb7d89a8c8a0eae87c23207`.
Параметры закреплены в `scripts/mac-runtime.json`; SHA проверяется и для кэша
`tmp/mac-runtime/node.tar.gz`. При несовпадении сборка прекращается.

Результат: `/Users/krisfeminova/projects/investment-portfolio/dist/mac-arm64`.
Внутри: `runtime/node` и лицензия Node, `server/main.js`, `server/migrations`
(включая `meta/_journal.json`), Angular в `web` вместе с `3rdpartylicenses.txt`, публичный T-Invest CA в `certs`,
launcher и npm-пакеты с лицензиями. Около 243 МБ. Переносить весь каталог,
сохраняя исполнимые биты и относительные симлинки (например, `cp -a`).

Nx явно оставляет npm-зависимости внешними (`externalDependencies: 'all'`).
Скрипт извлекает фактические external require из собранного webpack-файла,
включая `@fastify/static`, `exceljs`, `tslib` и `better-sqlite3`, и копирует
транзитивные dependencies, установленные optional dependencies и peers.
Опциональные Nest-адаптеры, которые не используются, не устанавливаются.
Дерево сохраняет раздельные версии пакетов pnpm, ссылки ведут только внутрь
артефакта. `build-manifest.json` содержит версии пакетов, список externals,
поставку Node и хеш lockfile. Сборка требует совпадения установленного lockfile
`node_modules/.pnpm/lock.yaml` с репозиторным.

Финальная проверка сборки выполняет реальный `SELECT 1` через `better-sqlite3`
вложенным Node. В текущем пакете 13.0.1 загружается
`prebuilds/darwin-arm64.node`. `otool -L` показал только системные библиотеки
для Node и SQLite, без Homebrew; Mach-O minimum macOS у обоих — 11.0.
Это не заменяет проверку на самой старой поддерживаемой системе.

Angular собирается с `CI=true` и `--skip-nx-cache`: локальный LMDB-кэш Angular
на этой машине вызывал нативный SIGABRT. Production-сборка встраивает CSS
Google Fonts, поэтому при сборке нужен интернет. Файлы шрифтов браузер пока
загружает с Google; сервер и работа с локальной БД от них не зависят.
Есть предупреждение существующего initial budget: 729.31 кБ при пороге 720 кБ;
порог ошибки 800 кБ не превышен.

## Контракт запуска для Swift

Запустить `start.sh` по абсолютному пути через `Process`, без shell-склейки
аргументов. Либо вызвать `<resources>/runtime/node` с единственным аргументом
`<resources>/launch.mjs`. Рабочий каталог произвольный. Node в PATH не нужен.
Хранить PID/объект Process launcher-а; при выходе приложения послать ему SIGTERM
и дождаться завершения. `start.sh` делает exec, его PID становится PID launcher-а.
Обёртка пересылает сигнал серверу, ждёт ребёнка и сохраняет его код/сигнал выхода.
Nest завершает HTTP, а Fastify onClose закрывает SQLite.

```sh
DATA_DIR="/абсолютный/путь/Данные" PORT=3000 \
  "/абсолютный/путь/mac-arm64/start.sh" &
pid=$!
curl --fail http://127.0.0.1:3000/api/health
kill -TERM "$pid"
wait "$pid"   # при завершении сигналом допустим ненулевой код
```

| Параметр | Значение |
| --- | --- |
| Ресурсы | Определяются по расположению launcher-а; APP_ROOT и STATIC_ROOT задаются им |
| DATA_DIR | Абсолютный пользовательский каталог; default `~/Library/Application Support/Investment Portfolio` |
| DB_PATH | Default `portfolio.sqlite` внутри DATA_DIR; относительный путь — от DATA_DIR, абсолютный используется как есть |
| ENV_FILE | Default `DATA_DIR/.env`; для переопределения передавать абсолютный путь |
| PORT | Default 3000, можно передать через окружение или пользовательский .env |
| API_HOST | В установленной версии принудительно `127.0.0.1`, даже если .env задаёт другой адрес |
| NODE_EXTRA_CA_CERTS | Передавать до запуска; T-Invest CA добавляет обёртка до дочернего Node |

Окружение имеет приоритет над `.env`. Launcher загружает пользовательский `.env`
до импорта обёртки; `load-env.ts` также работает раньше графа модулей SQLite.
Если уже есть корпоративный CA, объединённый файл пишется в
`DATA_DIR/tmp/extra-ca-certs.pem`, а не в ресурсы приложения. Из репозитория
без DATA_DIR сохранены прежние defaults: корневой `.env`,
`data/portfolio.sqlite`, `tmp/extra-ca-certs.pem`.

`GET /api/health` возвращает `{"status":"ok","spa":true}` только после
успешных миграций и регистрации SPA; дополнительно выполняет SQL и проверяет
доступность index.html и читаемость локальных JS/CSS, указанных в его script/link
(включая modulepreload). При потере файла после запуска health возвращает 503.
Отсутствие файлов запуска SPA или сломанные миграции останавливают
установленную версию с ошибкой до listen. Неизвестный `/api/*` и отсутствующие
файлы статики возвращают 404, без HTML SPA-fallback.

## Данные портфеля — задача 2А

Реализован маршрут `/data` («Данные» в меню): скачивание SQLite, загрузка с
предпросмотром и подтверждением замены, очистка с вводом слова `УДАЛИТЬ`.
Контракт DATA_DIR/DB_PATH/ENV_FILE и каталога миграций из задачи 1 сохранён.
Новые npm-зависимости не нужны. Пересобран `dist/mac-arm64`.

Формат копии — обычный SQLite 3, без архива, шифрования и внешних sidecar-файлов.
Имя: `portfolio-YYYY-MM-DD-HHmm.sqlite` (локальное время сервера). Снимок получен
через `better-sqlite3.backup()` (SQLite Backup API), включает зафиксированный WAL,
все таблицы и `__drizzle_migrations`; готовая копия переведена в journal_mode=DELETE.
В ней находятся операции, счета, системы, инструменты, идентификаторы, котировки,
история цен, импорта и прочие данные SQLite. Токен T-Invest/.env, настройки Mac и
браузера, исходные отчёты с диска не копируются. Место сохранения определяет
браузер: при автоматических загрузках нужно включить запрос папки либо использовать
«Сохранить ссылку как…». Облачная папка выбирается как обычная локальная папка.

Загрузка — бинарный поток application/octet-stream, отдельный предел 512 МиБ;
JSON-лимит 25 МиБ для импорта не менялся. Временные каталоги — `os.tmpdir()` с
правами 0700, файлы 0600. Неподтверждённые загрузки живут 15 минут (не более трёх),
удаляются по отмене, истечению срока, успешной замене и штатному завершению сервера.
После аварийного завершения временные файлы может убрать ОС.
Проверяются integrity_check, foreign_key_check, известный префикс хешей/времён
миграций, user_version/application_id и точная структура известной версии.
Миграции выполняются только над загруженной временной копией.

Рабочий файл не переименовывается и не заменяется: подготовленные таблицы целиком
переносятся через ATTACH в одной IMMEDIATE-транзакции существующего соединения.
Все Drizzle-клиенты продолжают читать это соединение. SQLite WAL обеспечивает
откат при исключении и аварийном завершении до COMMIT. Пока есть незавершённый
запрос Nest (в том числе GET с догрузкой котировок, импорт или T-Invest), замена
возвращает 409; повторить можно после завершения запроса. После замены меняется
поколение данных; старые мутации отвергаются до вызова сервисов. Все HTTP-мутации
теперь требуют X-Portfolio-Generation из GET /api/data/status; интерфейс и
scripts/test-mac-runtime.mjs обновлены. Кэш разобранных импортов инвалидируется.
Вкладки проверяют поколение каждые 3 секунды и при фокусе, затем перезагружаются.
Очистка/восстановление также требуют доверенного Origin и явного подтверждения;
production принимает только свой origin, dev дополнительно настроенный CORS_ORIGIN
(default http://localhost:4200); forwarded-host не используется как источник доверия.

### Точка повторного использования для 2Б

`apps/api/src/db/portfolio-backup.ts` экспортирует PortfolioBackup без импорта
живого client.ts и без зависимости от HTTP. Конструктор принимает абсолютный
каталог миграций. Методы: backup(connection, destination), temporary(),
prepare(temporaryFile) → { accounts, operations, systems },
replace(connection, preparedFile), clear(connection).

После реализации 2Б подготовка выполняется в profile/entry.ts ДО импорта
http-server.ts и client.ts (см. контракт 2Б ниже). MIGRATIONS_FOLDER экспортирован из db/run-migrations.ts;
в установленном runtime миграции по-прежнему лежат в server/migrations.
Для восстановления скопировать выбранный файл в temporary().file, вызвать
prepare(), после подтверждения replace(), затем dispose() в finally.
Не передавать пользовательский оригинал в prepare(): метод применяет миграции.
До HTTP нет незавершённых запросов; при вызове в работающем сервере обязательно
использовать ограждение dataGate, как в data-management/data-http.ts.
Перед replace() целевое соединение должно иметь актуальную схему. Метод
beforeCommit в replace предназначен для воспроизводимой проверки отказов.

## Первый запуск и обновление — задача 2Б

Точка входа main.ts теперь исполняет profile/entry.ts. Сначала читаются настройки,
берутся блокировки профиля, восстанавливается незавершённая публикация и готовится
база; только затем динамически импортируется http-server.ts и открывается
долгоживущее соединение client.ts. Объявления webpack-модулей сами по себе его
не открывают. Команды `profile` завершаются без HTTP и без импорта HTTP-графа.

В установленной версии первый запуск без БД возвращает ONBOARDING_REQUIRED,
вместо неявного создания пустой базы. Режим разработки сохраняет прежний пустой
старт. DATA_DIR по-прежнему переопределяет каталог профиля, DB_PATH считается от
него, абсолютный DB_PATH разрешён. Default установленной версии и CLI:
`~/Library/Application Support/Investment Portfolio/`.

Для переноса используется тот же PortfolioBackup: исходник открывается readonly
с fileMustExist, Backup API включает WAL, на отдельном локальном файле выполняются
проверки и все стадии миграций. Оригинал не мигрирует. Только готовый закрытый файл
публикуется в локальный профиль; отсутствие исходника впоследствии не мешает работе.
Неверный путь, повреждение и ошибка миграции не создают пустую рабочую базу.
`init-empty`, `restore`, `import-project` отказывают, если рабочая база уже есть.

Публикация первого профиля — атомарный hard link без перезаписи; публикация
обновлённой схемы — атомарный rename при закрытой БД, после checkpoint и закрытия
короткого подготовительного соединения. Подготовленный файл и журнал pending.json
локальны, записываются с fsync. После прерывания повторный вызов завершает уже
проверенную публикацию; если файлы изменились, возвращается RECOVERY_CONFLICT.
Блокировки SQLite отдельны от финансовой БД, удерживаются весь срок работы HTTP
и автоматически освобождаются также после аварийного завершения процесса.

### Вызовы из Swift

Запускать Process с executableURL `<resources>/start.sh` и массивом arguments
`["profile", action]`, без shell. Либо `<resources>/runtime/node` с аргументами
`["<resources>/launch.mjs", "profile", action]`. Передавать DATA_DIR только для
переопределения профиля. stdin — UTF-8 JSON, после записи закрыть pipe.
На stdout приходит ровно один JSON `{ok:true,action,result}`. При ошибке — exit 1
и JSON `{ok:false,error:{code,message}}` на stderr. Не выводить stdin/окружение
в журнал Swift: там может быть токен. Перед командой закрыть HTTP-процесс и
дождаться его завершения; PROFILE_BUSY означает, что профиль ещё занят.

| action | JSON stdin | Результат |
| --- | --- | --- |
| status | `{}` | exists, databasePath, tinvestConfigured, recovery; БД не создаётся |
| resolve-start | `{}` | launchPath сохранённого совместимого сервера после отката; null означает встроенный сервер. Текущая БД и отметка отката сохраняются |
| init-empty | `{}` | Пустая актуальная база и нулевые счётчики |
| inspect | `{"source":"/полный/путь/копия.sqlite"}` | accounts, operations, systems; исходник и рабочая база не изменяются |
| restore | `{"source":"/полный/путь/копия.sqlite"}` | Новый локальный профиль после проверки и миграций |
| import-project | `{"projectRoot":"/полный/путь/проект"}` | Перенос с DB_PATH из его .env |
| backup | `{"destination":"/полный/путь/копия.sqlite"}` | Автономный файл 2А; существующий файл не перезаписывается |
| import-tinvest | `{"sourceEnvFile":"/полный/путь/.env","confirmation":"IMPORT TBANK_TOKEN"}` | configured=true, restartRequired=true |
| prepare-update | `{}` | backupDirectory с совместимой парой перед заменой приложения |
| recover-update | `{"directory":"/профиль/backups/update-…","confirmation":"RESTORE UPDATE BACKUP"}` | launchPath прежнего runtime и safetyBackup текущей пары |

В import-project доступны явные dbPath, dataDir, envFile. Относительный DB_PATH
считается от DATA_DIR старого проекта, если он задан; иначе от projectRoot.
При отсутствии DB_PATH используются portfolio.sqlite при DATA_DIR либо
projectRoot/data/portfolio.sqlite. Для старого запуска с переопределениями
окружения передать фактические dbPath/dataDir явно. Относительный старый DATA_DIR
считается от projectRoot; если dev запускали из другого cwd, передать абсолютный.
Настройки исходника не загружаются в окружение нового приложения.

Перенос T-Invest всегда отдельный: разрешён только TBANK_TOKEN, сетевые параметры,
порты, CA и пути не копируются. Вместо sourceEnvFile допускается token через stdin.
Для замены существующего токена дополнительно требуется replaceExisting=true.
Токен хранится в активном ENV_FILE (default DATA_DIR/.env) с правами 0600, каталог профиля — 0700; в результат
и ошибки значение не попадает. Передача секретов через аргументы процесса не нужна.

### Обновление и откат

При успешном старте установленной версии сохраняется её автономный runtime
(Node, сервер, миграции, web и зависимости) в закрытом каталоге профиля .profile.
Это текущий артефакт задачи 1, ещё не Swift .app. Обновляющий код сначала вызывает
prepare-update в прежней версии и сохраняет возвращённый backupDirectory.
Для прежнего runtime, ещё не имеющего этой команды, можно вызвать команду в новой
версии с `{"previousApplication":"/полный/путь/прежние ресурсы"}`, пока прежние
ресурсы ещё не удалены. Схема копии должна точно соответствовать комплекту миграций
выбранной версии приложения; при несовпадении обновление останавливается.

При обычном запуске новой версии с ожидающими миграциями автоматически создаётся
ещё одна актуальная предмиграционная пара в DATA_DIR/backups/update-…:
portfolio.sqlite, application/ и recovery.json с контрольной суммой базы и
идентификатором приложения. Миграции выполняются на следующей временной копии,
а не на рабочей БД и не на сохранённом предмиграционном файле. При сбое остаются
прежняя рабочая база и готовая пара. Если прежние ресурсы не были сохранены,
UPDATE_PREPARATION_REQUIRED останавливает изменение схемы; старую версию нельзя
восстановить из уже удалённых ресурсов.

recover-update принимает только локальную пару из backups этого профиля,
проверяет контрольную сумму и соответствие схемы приложению, создаёт safetyBackup
нынешней пары, затем восстанавливает прежнюю базу БЕЗ миграций новой версии.
После этого запускать возвращённый launchPath с тем же DATA_DIR/DB_PATH.
Новая версия откажет с RECOVERY_APPLICATION_REQUIRED, чтобы случайно не мигрировать
восстановленную базу обратно. Повторная подготовка обновления с подходящей прежней
версией снимает это ограничение. Ресурсы прежних версий и пары автоматически не
удаляются: политика очистки должна сохранять используемые пути отката.
