## 1. Проблемы (диагноз уже сделан, не переисследуй с нуля)

1. **Три цифры доходности за период.** «Текущий год» на копии БД пользователя: ROI +11,49%,
   XIRR +11,34%, график «Портфель против рынка» +8,6%. Реализованное + выплаты совпадают
   (335,5 тыс. ₽), расходится база:
   - ROI берёт нереализованное за **всю историю** удерживаемых позиций (+107,7 тыс. ₽
     заработаны до 1 января), а знаменатель — себестоимость текущих позиций;
   - XIRR сворачивает капитал до периода в отток **по себестоимости**, а не по рыночной
     стоимости на начало периода;
   - график — изменение богатства за период с очисткой от ввода/вывода (TWR).
   Корень: два независимых расчёта (`effectiveness()` + `periodCashFlows`/`xirr` на
   бэке; `timeWeightedIndex` на фронте через `entities/valuation` → `portfolioIndex`),
   к тому же часть на `number`.
2. **«Стоимость инструментов во времени»** рисует только `marketValueRub`: продажа и
   выплаты выглядят как потеря (07.09.2026 — провал ≈371 тыс. ₽: деньги от продаж лежали
   в кэше, кэш на графике не показан).
3. **Бенчмарк нечестный:** портфель с дивидендами против ценового IMOEX; «Депозит» —
   константа 16% (`DEPOSIT_ANNUAL_RATE` в `widgets/benchmark-chart`).
4. **Невидимые пропуски журнала:** если Dividend/Coupon не импортирован, никто об этом
   не знает.

## 2. Архитектурное решение

### 2.1. Единый источник истины: «контур» + один расчёт периода

Все цифры периода — из **одной чистой функции в `libs/core`**, поверх уже существующего
дневного ряда `valuationSeries`:

```
operations + price_history ─► valuationSeries (есть) ─► periodPerformance(контур, from, till)
                                                              │
                         GET /api/performance  (один DTO) ◄───┘
                                │
        карточки · «Портфель против рынка» · таблица эффективности · страница системы
```

Ключевое понятие — **контур** (boundary): что считаем «капиталом» и что — «внешним
потоком». Для любого контура на каждый день есть стоимость `V_t` и внешний поток `F_t`:

| Контур | `V_t` (капитал) | `F_t` (внешний поток, + = деньги внутрь) |
|---|---|---|
| Весь портфель / портфель (есть свой кэш) | богатство = позиции + кэш = чистый ввод + `totalRub` | Deposit − Withdraw |
| Система / инструмент (своего кэша нет) | `marketValueRub` группы | покупки − выручка продаж − выплаты |

Из пары рядов (`V`, `F`) получается всё остальное — **одними формулами для всех
контуров**:

- **Результат за период, ₽** = `V_end − V_start − ΣF`. Инвариант: равно
  `Δ fixedRub + Δ unrealizedRub` из `rebaseToPeriod` и разложению на реализованное /
  выплаты / переоценку за период.
- **TWR** — цепочка дневных доходностей (текущая логика `timeWeightedIndex`: ввод в
  начале дня, вывод в конце, при `V ≤ 0` день нулевой). Ряд индекса для графика и
  итоговая цифра карточки — **один и тот же массив**, последняя точка = карточка.
- **MWR / XIRR** — `xirr` по потокам: отток `V_start` **по рыночной стоимости** на дату
  `from` (а не себестоимость), внешние потоки на их даты, приток `V_end` на `till`.
  Для «Всё время» `V_start = 0` → совпадает с нынешним смыслом.
- **Средний капитал периода** (Modified Dietz) = `V_start + Σ w_i·F_i`, где
  `w_i` = доля периода, в течение которой поток работал. Нужен как знаменатель
  «результат / капитал» и как проверка XIRR.

Деньги — `Decimal` по всему расчёту; наружу decimal-строки, коэффициенты (%, индекс) —
`number`. Переписать `timeWeightedIndex` на `Decimal` (с тем же поведением, тесты не
должны поменяться). Фронт **больше ничего не считает** (`portfolioIndex` удалить),
только рисует DTO.

Фьючерсы: в портфельном контуре их результат уже в богатстве (через кэш) — отдельной
ветки не нужно. В контуре «система ЮВ1» (только фьючерсы, `V ≈ 0`) TWR/MWR не
определены → `null` с причиной «нет капитала» (согласовано ранее: метрики в % от
капитала/ГО не считаем).

### 2.2. Определения метрик и UI

| Карточка | Определение | Отвечает на вопрос |
|---|---|---|
| **Результат, ₽** | `V_end − V_start − ΣF`, с разбивкой: реализованное, выплаты, переоценка за период | сколько заработал за период |
| **Доходность стратегии (TWR), %** | цепочка дневных доходностей; = последняя точка «Портфель против рынка» | насколько хорошо работал капитал, независимо от того, когда вы вносили деньги; **сравнима с бенчмарком** |
| **Доходность ваших денег (XIRR), % годовых** | MWR с рыночной базой на начало периода | сколько годовых дали именно ваши деньги с учётом сумм и дат вводов |

- Нынешний **ROI «результат / себестоимость текущих позиций» с дашборда убрать** как
  метрику периода: у него несопоставимые числитель и знаменатель. Отношение к
  себестоимости остаётся там, где оно осмысленно — в таблицах позиций/сделок
  («доходность позиции к цене покупки»), подписанное именно так.
- XIRR для периода < 365 дней в годовых вводит в заблуждение (короткий период
  аннуализируется в огромные числа). Для коротких периодов показывать MWR **за период**
  (Dietz: результат / средний капитал), для ≥ 1 года — XIRR в годовых. Подпись
  карточки меняется вместе с базой; правило — в `libs/core`, не в шаблоне.
- У каждой карточки тултип с определением одной фразой и бейдж-связка «= график» для TWR.
- Таблица эффективности по системам/портфелям (`widgets/effectiveness-table`) — те же
  три колонки, каждая строка — `periodPerformance` своего контура.
- TWR и XIRR могут **законно** расходиться (довнесения перед ростом/падением) —
  объяснение в тултипе, а не «баг».

### 2.3. График «Стоимость инструментов во времени»

Решение: **стек позиций + верхний слой «Деньги»**, вершина стека = богатство `V_t`.

- Кэш на день = `V_t − Σ marketValueRub` (портфельный контур). Продажа переливает
  стоимость из слоя бумаги в слой «Деньги» — вершина не падает; купон/дивиденд
  добавляют в «Деньги». Провал 07.09 исчезает, потому что деньги были на счёте.
- Маркеры событий на оси времени: выплата (сумма, бумага), продажа (сумма) — в тултипе.
- Почему не «накопленные выплаты отдельной линией»: выплаты реинвестируются — линия
  задвоит их с позициями, и у неё другой масштаб/смысл; почему не только маркеры: сумма
  по-прежнему проваливается.
- Контур без кэша (фильтр по системе/инструменту): слоя «Деньги» нет, только позиции +
  маркеры продаж/выплат и подпись «деньги от продаж и выплат уходят в общий кэш
  портфеля».
- Кэш, вычисленный как `V − позиции`, сверить с `cashBalanceRub` (`libs/core/cash.ts`) на
  сегодня — должен совпасть (тест). Отрицательный вычисленный кэш = в журнале не хватает
  ввода денег → сигнал полноты (§2.5).

### 2.4. Бенчмарк

Проверено: MOEX ISS `history/engines/stock/markets/index/securities/{SECID}` отдаёт
**MCFTR** (полной доходности, брутто), **MCFTRR** (полной доходности, нетто — дивиденды
за вычетом налога для резидентов), **IMOEX** (ценовой), **RGBITR** (ОФЗ, полной
доходности), **RUCBTRNS** (корпоративные облигации), **RUSFAR** (ставка денежного рынка,
% годовых — это ставка, не индекс).

- Индексы хранить в `price_history` как инструменты вида `index:MCFTRR` и догружать тем
  же `PriceHistoryService.ensure` — отдельный путь `getIndexHistory` для бенчмарка
  убрать (один механизм истории).
- **Ориентир по умолчанию — MCFTRR**: дивиденды в журнале пользователя приходят «налог
  удержан», значит честное сравнение — с нетто-индексом полной доходности. IMOEX
  оставить выбираемым с подписью «ценовой, без дивидендов».
- Выбор ориентира (MCFTRR / RGBITR / RUCBTRNS / IMOEX) — переключатель в виджете, в URL.
  Смесь индексов по весам портфеля — **не делать** (YAGNI), отметить в roadmap.
- **«Депозит» заменить на «Денежный рынок (RUSFAR)»**: индекс = цепочка
  `(1 + RUSFAR_d / 100 × дни / 365)` по фактическим дневным ставкам; константу 16% удалить.
- Сравнение: ориентир ребазируется в 100 на первый день периода и сравнивается с
  **TWR** портфеля (обе — доходность без учёта ваших потоков). Опционально (отдельный
  коммит, если останется время): линия «те же вводы в индекс» — симуляция ваших
  `F_t` в MCFTRR, её корректно сравнивать с XIRR.

### 2.5. Полнота журнала — да, нужен сигнал

Отдельная чистая функция в `libs/core` (`journalCompleteness`) → список предупреждений
с инструментом, датой и причиной; на дашборде — один индикатор «Данные: N
предупреждений» со списком (рядом с уже существующими пометками `carried` / «нет цены»,
в одном месте). Метрики не блокируются, но карточка периода, задетого
предупреждением, помечается.

Проверки:
- **Купоны:** по графику купонов MOEX ISS
  (`/iss/statistics/engines/stock/markets/bonds/bondization/{SECID}.json`) — бумага
  удерживалась на дату фиксации, а Coupon-операции в окне N дней после выплаты нет.
- **Дивиденды:** `/iss/securities/{SECID}/dividends.json` (дата отсечки, сумма) —
  удерживалась на отсечку, Dividend-операции в окне N дней после нет. Проверь, что
  эндпоинт отдаёт данные; если нет — проверку пропустить, не придумывать.
- **Кэш:** вычисленный кэш (§2.3) уходит ниже нуля → не хватает Deposit.
- Расписания купонов/дивидендов кэшировать в БД с датой загрузки (таблица — на твой
  выбор, обоснуй), сеть — только через провайдер с тестами на зафиксированных ответах.
- Срок N и пороги — константы с комментарием, в одном месте.

## 3. Чего не делать

- Не держать старый и новый расчёт параллельно после переключения: `effectiveness()`
  (формулы ROI/XIRR) и `periodCashFlows`, если он больше нигде не нужен, — удалить.
- Не менять `valuationSeries` по смыслу (кроме того, что нужно для `F_t` контура).
- Не пересчитывать ничего на фронте.
- Не проверять UI кликами самому — `tsc`/`lint`/`test` и чек-лист пользователю.

## 4. Этапы

**Этап 0. Эталоны до изменений (обязательно первым).**
- Скриптом на копии БД пользователя (не на рабочей; путь спроси, если не найдёшь)
  зафиксировать текущие цифры: «Всё время» — результат ₽, реализованное + выплаты,
  стоимость, ROI/XIRR/последняя точка графика; «Текущий год» — 11,49 / 11,34 / 8,6 и
  335,5 тыс. ₽, +107,7 тыс. ₽ дорежимной переоценки. Результат — таблица в отчёте.
- Синтетические фикстуры в `libs/core` с ручным расчётом (в коммит): без потоков
  (TWR = MWR = простая доходность), ввод в середине периода перед ростом (TWR ≠ MWR,
  оба посчитаны руками), продажа в кэш (богатство не меняется), купон, вывод денег,
  период, начинающийся с открытыми позициями (база по рынку, не по себестоимости).

**Этап 1. Ядро.** `periodPerformance` + контуры + `Decimal`. Тесты-инварианты:
- результат ₽ = Δ fixed + Δ unrealized = сумма разбивки;
- последняя точка индекса = TWR карточки (тождественно, один массив);
- аддитивность ₽: результат(янв–июн) + результат(июл–дек) = результат(год);
- «Всё время»: результат ₽ и XIRR совпадают с эталоном этапа 0 (в пределах копейки /
  0,01 п.п.); TWR «Текущий год» = 8,6% эталона;
- сумма результатов систем = результат портфеля (₽), если в портфеле нет
  непривязанных выплат — иначе разница ровно на них.

**Этап 2. API и переключение потребителей.** `GET /api/performance?scope&id&from&till`
(Zod-DTO в `schemas.ts`: результат и разбивка, TWR + ряд индекса, MWR/XIRR с типом
«за период / годовых», средний капитал, предупреждения). Карточки, «Портфель против
рынка», таблица эффективности, страница системы — на него. Удалить мёртвый код.

**Этап 3. Бенчмарк.** Индексы в `price_history`, MCFTRR по умолчанию, переключатель,
RUSFAR вместо 16%.

**Этап 4. График стоимости.** Слой «Деньги» + маркеры; тест «кэш на сегодня =
`cashBalanceRub`».

**Этап 5. Полнота журнала.** Провайдеры расписаний, `journalCompleteness`, индикатор.

**Этап 6. Документация.** `docs/02-data-model.md`: контур, определения трёх метрик,
почему TWR ≠ XIRR, бенчмарки; `docs/04-roadmap.md`.

## 5. Риски

- **Проценты «Всё время» сменят смысл** (ROI → TWR/XIRR): рубли не должны измениться,
  проценты — могут. Показать пользователю «было → стало» с объяснением до этапа 2.
- Точность TWR на днях с почти нулевым капиталом (уже был баг −81%): сохранить
  правило «ввод в начале дня, вывод в конце», добавить тест на ввод при почти нулевом
  остатке.
- Пропущенные Deposit/Withdraw ломают TWR (довнесение выглядит как прибыль) —
  именно поэтому проверка кэша в §2.5.
- Дыры в истории цен (`carried`) влияют на `V_start`/`V_end` — помечать карточку.
