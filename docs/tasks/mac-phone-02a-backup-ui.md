# 2А. Резервная копия, восстановление и очистка через интерфейс

Работай в проекте investment-portfolio. Реализуй эту задачу до 2Б, чтобы резервную копию можно было создать уже в текущем веб-интерфейсе на Mac. Прочитай `CLAUDE.md`, `apps/api/src/db/client.ts`, `apps/api/src/db/apply-migrations.ts` и `apps/web/src/app/app.routes.ts`. Согласуй запуск и пути с актуальным кодом задачи 1. Проверки выполняй на временных профилях.

## Пользовательский сценарий

Добавь в навигацию раздел «Данные» с тремя действиями.

1. **Скачать резервную копию.** В один самодостаточный файл вида `portfolio-2026-11-14-1830.sqlite` сохраняется согласованный снимок всей базы приложения, включая зафиксированные записи в WAL и историю миграций. Используй SQLite Backup API. Пользователь сам выбирает место хранения готового файла, в том числе папку облачного диска. Файл содержит финансовые данные в читаемом виде. Укажи это рядом с кнопкой. Токен T-Invest, настройки Mac, настройки браузера и исходные файлы отчётов с диска остаются вне копии.
2. **Восстановить из файла.** При выборе файла покажи, какой портфель будет восстановлен (например, количество счетов и операций), и объясни, что текущие данные будут заменены целиком. Дождись подтверждения. Подготовь восстановление во временном каталоге. Проверь тип и целостность базы и совместимость схемы, примени поддерживаемые миграции к копии. Для базы более новой, неизвестной или повреждённой версии покажи понятную ошибку и сохрани рабочую базу. Используй загрузку файла, подходящую для реального размера портфеля, учитывай действующие лимиты сервера.
3. **Удалить все данные портфеля.** Объясни, что именно будет очищено, предложи скачать копию, затем запроси отдельное явное подтверждение. После удаления открывается пустой рабочий портфель. Пользователь может сразу создать первую запись или восстановить файл. Скачанные ранее копии и настройки подключения сохраняются. Отмена любого диалога оставляет данные на месте.

## Целостность и повторное использование

Реализуй операции резервирования, проверки и восстановления в общем серверном коде. В задаче 2Б тот же механизм будет вызываться до запуска HTTP. Действия из веб-интерфейса должны работать и при уже открытой базе. Учти единственное долгоживущее соединение SQLite, параллельные записи, чужие вкладки и незавершённые импорты. После переключения профиля все запросы должны обращаться к актуальным данным. Не меняй живой .sqlite под открытым соединением. При ошибке или прерывании восстановления рабочий профиль должен оставаться согласованным. После успешной смены данных обнови открытый экран. Для разрушающих действий проверь источник запроса на сервере с учётом production- и dev-режимов. Для служебных файлов используй пользовательские временные каталоги с уборкой.

## Как принять

На профиле А создай связанные данные и снимок с записями в WAL. Перенеси только скачанный файл в отдельный чистый профиль Б. Сверь данные и итог портфеля при одинаковых котировках. Проверь отмену, полную очистку, восстановление поверх другого заполненного профиля, более новую и повреждённую базы, сбой во время восстановления, параллельную запись и обновление экрана. Убедись, что новая операция после восстановления сохраняется после перезапуска. По возможности пройди путь «скачать → очистить → восстановить» через браузер.

Верни ветку и коммит либо состояние diff, команды и результаты проверок, точное описание формата файла и точку вызова для задачи 2Б. Отдельно укажи, что проверено через интерфейс.
