## 1. Проблема

Один актив приходит из разных источников (xlsx-отчёт, HTML-отчёт, CSV, API Т-Банка)
под разными кодами, `ImportService.ensureInstruments` не находит совпадения по
тикеру/ISIN/названию и заводит дубль:

- `TMON` (xlsx) и `TMON@` (API, «Денежный рынок»). «@» срезает только
  `tbank-xlsx-report.ts` (`normalizeTicker`). У дубля `market_source = manual`, нет цены
  и истории цен.
- `RU000A10B4K3` и `TCS00A10B4K3` — ГМК Норникель БО-001Р-08 (подтверждено в комментарии
  `tbank-sync.service.ts`, `loadInstruments`). `TCS00…` — внутренний код Т-Банка, **не
  ISIN** (нет кода страны, контрольная цифра не сходится).

Ручное «Слить» (`PortfoliosService.mergeInstruments`) переписывает `instrument_id` у
операций и удаляет источник, но **нигде не запоминает** решение — после удаления
сделок и повторного импорта дубль возвращается.

Сопутствующие дефекты, которые нашлись при разборе:
- `RawRow` не имеет отдельных полей идентификаторов: тикер то тикер, то ISIN.
  Парсер API Т-Банка складывает `ticker || isin || figi` в одно поле `ticker` — ISIN и
  figi теряются.
- Регэкспы ISIN разные в трёх местах (`import.service.ts`, `broker-html-report.ts`,
  `tbank-xlsx-report.ts`), только для `RU`.
- `id` инструмента = сырой тикер (`id: raw.ticker`), отсюда id `TMON@`.
- `mergeInstruments` не в транзакции.

## 2. Архитектурное решение

Две разные задачи — два разных механизма:

| | Нормализация кода | Сопоставление идентичностей |
|---|---|---|
| Природа | детерминированное правило (`TMON@` → `TMON`) | решение человека или сильный идентификатор (`TCS00A10B4K3` = `RU000A10B4K3`) |
| Где живёт | **код** в `libs/core`, чистая функция | **данные** в БД, таблица идентификаторов |
| Когда применяется | ко всем строкам всех источников, до резолва | при резолве инструмента |

### 2.1. Конвейер импорта

```
парсер (любой) ──► normalizeRawRows (@core) ──► resolve (идентификаторы → инструмент) ──► preview/commit
```

- Нормализация — **общий шаг в `libs/core`** между парсером и сервисом, а не в каждом
  парсере (дублирование, легко забыть в новом) и не размазана по `ImportService`
  (доменное правило должно быть чистым и тестируемым без БД). `ImportService`
  вызывает его в одной точке — там, где сходятся все источники, включая синк Т-Банка
  (`resolveRawRows` / `parseFile` — проверь, что действительно все пути проходят
  через неё).
- Правила — список маленьких чистых функций (Chain/Strategy): срезать хвостовой «@»,
  trim, верхний регистр кодов. Требования к правилу: детерминированное, идемпотентное,
  не зависящее от источника. **Специфика конкретного брокера (`TCS00…`) — не
  нормализация**, её решают идентификаторы.
- Убрать `normalizeTicker` из `tbank-xlsx-report.ts` (теперь общий шаг).

### 2.2. Идентификаторы в `RawRow`

Добавить в `RawRow` структурированные идентификаторы:
`identifiers?: { isin?: string; figi?: string; tbankUid?: string; brokerCode?: string }`.
Каждый парсер заполняет то, что реально знает:
- API Т-Банка — `figi`, `instrumentUid`, `isin`; `ticker` — только биржевой тикер.
  Если `isin` не валиден (например, `TCS00A10B4K3`) — это `brokerCode`, не `isin`.
- HTML-отчёт — ISIN из «Справочника ЦБ».
- xlsx — ISIN из ячейки «ISIN: …».
- CSV — опциональная колонка `isin`.

Один валидатор ISIN в `libs/core` (формат + код страны + контрольная цифра по Луну),
заменяет три регэкспа.

### 2.3. Хранение: таблица `instrument_identifiers`

```
instrument_identifiers(
  scheme   text  -- 'ticker' | 'isin' | 'figi' | 'tbank_uid' | 'broker_code' | 'name'
  value    text  -- нормализованное значение
  instrument_id text → instruments.id  ON DELETE CASCADE
  origin   text  -- 'import' | 'merge' | 'manual'
  created_at
  PRIMARY KEY (scheme, value)
)
```

Почему так, а не иначе:
- **Не поля в `instruments`**: у одного актива много кодов (`TMON`, `TMON@`, `TCS00…`,
  `RU000…`, figi, uid), колонки не масштабируются, и у связи нужно происхождение.
- **Не таблица правил**: правила (regex) — это нормализация, им место в коде с тестами.
- **Не «только ISIN/figi»**: у CSV/HTML нет figi, у части бумаг нет настоящего ISIN,
  у брокера бывает суррогатный код. Сильные идентификаторы хранятся в **этой же**
  таблице как схемы `isin`/`figi`/`tbank_uid` — без новых колонок в `instruments`.
- Схема `scheme` + `value` вместо голого `alias`: `TMON` как тикер и как код брокера —
  разные факты, не смешиваем.
- `instruments.ticker` / `isin` остаются отображаемыми полями; **резолв идёт только
  через `instrument_identifiers`**. Миграция заполняет таблицу из существующих
  `instruments` (ticker, isin, name).

### 2.4. Резолв (чистая функция в `libs/core`)

`resolveInstrumentIdentity(row, index)` → `{ instrumentId | null, via, conflict?, suggestions[] }`.
Порядок по силе: `figi` / `tbank_uid` → валидный `isin` → `broker_code` → `ticker` →
`name` (только при совпадении типа и валюты).

- **Совпал идентификатор** → инструмент найден автоматически. Новые идентификаторы
  строки (например, figi, которого ещё не было) дописываются к нему с `origin = 'import'`.
- **Идентификаторы строки указывают на РАЗНЫЕ инструменты** (тикер → A, ISIN → B) →
  строка `error` с объяснением; ничего не склеиваем автоматически.
- **Совпадение только эвристическое** (похожий хвост `TCS00A10B4K3` ↔ `RU000A10B4K3`,
  близкое название) → **не связываем**, а предлагаем: строка `warn` с подсказкой
  «возможно, это …». Связь появляется только по решению пользователя.
- Существующий кросс-резолв внутри батча (имя → инструмент, случай LKOH) сохранить —
  но через тот же механизм, с покрытием тестами `import.spec.ts`, без регресса.
- Эвристики подсказок — отдельные чистые функции (OCP: новая эвристика — новая
  функция), не влияют на автоматический резолв.

### 2.5. Как пользователь разрешает неопознанный инструмент

Один доменный сервис `InstrumentIdentityService` (API) — единственный, кто пишет в
`instrument_identifiers`: `link(identifiers, instrumentId, origin)`, `merge(source, target)`.

1. **Основной путь — в предпросмотре импорта (до появления дубля).** Для строки с
   новым инструментом: «Создать новый» или «Это существующий: [выбор, подсказки
   сверху]». Выбор записывает идентификаторы строки с `origin = 'manual'` при
   подтверждении импорта → дубль не создаётся, следующий импорт резолвит сам.
2. **Исправление после факта — «Слить» остаётся**, но теперь это то же решение:
   в одной транзакции переносит операции, историю цен и котировку (как сейчас),
   **переносит все идентификаторы источника на цель** и добавляет `origin = 'merge'`,
   затем удаляет источник. Повторный импорт после удаления сделок резолвится в цель.
3. **Синк Т-Банка без предпросмотра**: новый инструмент создаётся (синк не блокируем),
   а в справочнике есть список «Возможные дубли» (те же эвристики подсказок) с кнопкой
   «Слить» — чтобы не искать дубли глазами.

Удаление: `ON DELETE CASCADE` — идентификаторы удалённого инструмента уходят вместе с
ним (висячих ссылок нет). Слияние удаляет источник только **после** переноса его
идентификаторов. Удаление сделок/систем/портфелей справочник и идентификаторы не
трогает — это знание, а не данные операций. Отдельная «очистка неиспользуемых
инструментов» в эту задачу не входит; если понадобится — она обязана предупреждать,
что теряются выученные связи.

### 2.6. Id новых инструментов

Не менять id существующих (это PK, на него ссылаются операции, история цен, котировки).
Новые инструменты получают id из **нормализованного** кода (не `TMON@`), коллизия id —
ошибка резолва, а не `onConflictDoNothing` (сейчас коллизия молча привязывает строку к
чужому инструменту — проверь и закрой тестом).

## 3. Этапы

1. **Ядро:** валидатор ISIN, `normalizeRawRows` с правилами, `identifiers` в `RawRow`,
   `resolveInstrumentIdentity`, эвристики подсказок. Тесты: `TMON@`→`TMON`,
   идемпотентность, `TCS00A10B4K3` не ISIN, валидные ISIN (`RU000A10B4K3`, `RU0009029540`),
   конфликт идентификаторов, приоритет схем.
2. **Парсеры:** заполнение `identifiers` во всех четырёх; убрать локальные
   нормализацию и регэкспы. Обновить спеки парсеров.
3. **БД и сервис:** миграция `instrument_identifiers` с заполнением из `instruments`;
   `InstrumentIdentityService`; `ImportService` резолвит через него (`ensureInstruments`
   и `buildResolvers` — одна логика, не две копии карт как сейчас); `mergeInstruments`
   → транзакция + перенос идентификаторов. Тест-сценарий пользователя: импорт →
   слить → удалить сделки → повторный импорт → **дубля нет**.
4. **Существующие дубли (миграция данных):**
   - Детерминированные (нормализованный тикер совпал с существующим инструментом того
     же типа и валюты, `TMON@` → `TMON`) — скрипт/миграция через **тот же** код слияния,
     не отдельным SQL.
   - Если пары нет (`TMON@` один) — не переименовывать id; поправить `ticker`, добавить
     идентификаторы, предложить пользователю выбрать источник цен.
   - Недетерминированные (`TCS00…` ↔ `RU000…`) — **автоматически не трогать**: они
     попадут в «Возможные дубли», пользователь сливает руками.
   - Безопасность: режим dry-run (печатает план), резервная копия файла БД перед
     применением, всё в одной транзакции, проверка инвариантов до/после: число
     операций не изменилось; по каждому портфелю количество позиций, вложено,
     реализованный P&L и кэш (`/api/operations/summary`) совпадают; меняется только
     оценка инструмента, у которого появилась цена. Расхождение → откат и отчёт.
5. **UI:** выбор «новый / существующий» для неопознанного инструмента в предпросмотре
   импорта (`pages/import`); список «Возможные дубли» рядом с `features/merge-instrument`.
   FSD-границы, Signal Forms/сигналы по `CLAUDE.md`.
6. **Документация:** `docs/02-data-model.md` (идентификаторы, нормализация, политика
   неоднозначности), `docs/04-roadmap.md`.
