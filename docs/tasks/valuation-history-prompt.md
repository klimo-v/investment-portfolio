## 0. Ветка и порядок работы

- Работаем **в текущей ветке `feat/system-performance`**, новую ветку не создаём.
- Перед началом `git status` должен быть чистым. Если нет — остановись и спроси

  данные снимков перенесены.

## 1. Проблема

1. На странице системы (`pages/system`, `widgets/system-equity-chart`) кривая эквити
   строится только по закрытым сделкам. У долгих систем («ядро», «акции без стратегии»)
   последняя точка — дата последней закрытой сделки (7 сентября 2026): не видно текущего
   результата, не учтены частичные продажи (SBMM, +94 439 ₽), дивиденды (+81 762 ₽),
   переоценка остатка (+188 671 ₽). Последняя точка 211 433 ₽ при полном результате
   576 306 ₽. Просадка «ядра» — 0, потому что кривая видит только три прибыльных закрытия.
2. Снимки (`portfolio_snapshots`, `snapshot_positions`) хранят **уже посчитанный итог**,
   а не исходные данные. Правка операции задним числом их портит, пересчитать не из
   чего — отсюда целая подсистема `snapshot_invalidations` / `staleness` /
   `features/snapshot-changes`. История есть только за дни нажатия кнопки, системы в
   снимке нет.

## 2. Архитектурное решение

**Храним только факты, всё производное — чистая функция.**

- Факты: журнал операций (есть) + **история цен** `price_history` (новое) + история
  курсов валют (в той же таблице, как отдельные «инструменты» или отдельной таблицей —
  реши и обоснуй, но одним механизмом заполнения).
- Производное: `valuationSeries(...)` в `libs/core` — дневной ряд, из которого строятся
  ВСЕ графики динамики: стоимость портфеля, стоимость инструментов, кривая системы.
- Готовые ряды в БД **не сохраняем**. Если понадобится скорость — кэш в памяти,
  сбрасываемый по ревизии данных, а не хранилище (его не нужно инвалидировать).
- Две кривые системы — **две разные величины**, не одна с новым смыслом:

| | Кривая по закрытым сделкам (есть) | Результат системы (новая) |
|---|---|---|
| Вопрос | качество входов/выходов | как реально менялись деньги системы |
| Точки | по одной на закрытую сделку | каждый день |
| Состав | только закрытые сделки | зафиксированное (все продажи, в т.ч. частичные; дивиденды/купоны по дате выплаты; минус комиссии и налоги) + переоценка остатка по цене дня |
| Метрики | win rate, profit factor, payoff, матожидание, серии | просадка, Sharpe, Sortino, recovery factor |

Кривую по закрытым сделкам **не менять** (кроме того, что риск-метрики уезжают на
новую кривую — см. этап 4).

## 3. Этапы

### Этап 1. Зафиксированный результат по дням + точка «сегодня» (без истории цен)

Быстро закрывает видимую проблему и не зависит от этапов 2–3.

- В `libs/core` функция дневного **зафиксированного** результата по набору операций
  (система/портфель): реализованный результат каждой продажи (в т.ч. частичной) на её
  дату, выплаты на дату выплаты, комиссии/налоги. Переиспользуй расчёт реализованного
  из `engine.ts` (`realizedPnlInRange` и т.п.) — **не пиши вторую формулу**.
- В DTO производительности системы — точка «сегодня» = зафиксированное + нереализованный
  по текущим котировкам, отдельным полем.
- Инвариант (тест): последняя точка зафиксированного + нереализованный = «Всего» системы
  в текущих карточках (`system-kpis`). На эталоне «ядра» должно сойтись с 576 306 ₽ —
  проверь по реальной БД и приведи цифры в отчёте.
- UI: переключатель «Закрытые сделки / Результат системы» в `system-equity-chart`,
  состояние в URL (`shared/query-param.ts`); «сегодня» — пунктирный хвост.

### Этап 2. `price_history` и её заполнение

- Таблица `price_history`: `instrument_id`, `date`, `price` (decimal-строка),
  `currency` (валюта цены — как в `quotes`), `accrued_interest` + `accrued_currency`
  (НКД облигаций, как в `quotes`), `source` (`moex` | `cbr` | `binance` | `manual` |
  `snapshot` | `broker-report`), PK (`instrument_id`, `date`). Drizzle-миграция.
- Источники — расширение существующих провайдеров через **узкий отдельный интерфейс**
  (ISP), а не раздувание `PriceProvider`: например, `PriceHistoryProvider.getHistory(
  ticker, from, till)`. Адаптеры:
  - MOEX ISS history: акции/ETF; облигации **с НКД на дату** (`ACCINT`) — без НКД стоимость
    облигаций по истории будет занижена; фьючерсы (engine futures / market forts).
    Запрос к ISS history уже есть в `getIndexHistory` — переиспользуй пагинацию.
  - ЦБ: история курсов валют (для пересчёта в ₽ на каждую дату).
  - Binance: дневные свечи (klines) для крипты.
  - Расчётные цены фьючерсов из отчётов брокера (то, что сейчас пишется в `quotes` при
    импорте) — дублировать в `price_history` с `source = 'broker-report'`.
- Заполнение **по требованию**: сервис `PriceHistoryService.ensure(instrumentIds, from,
  till)` догружает только отсутствующие диапазоны, вызывается перед расчётом ряда.
  Неудачная загрузка не роняет расчёт — день помечается как «нет цены».
- «Обновить цены» (`QuotesService.refreshAll`) дополнительно пишет цену дня в
  `price_history` (upsert) — это и есть «снимок», но факта, а не итога.
- Приоритет источников при конфликте на одну дату — одна явная политика (биржа >
  отчёт брокера > snapshot > manual или обоснуй иной), в одном месте.
- **Миграция данных снимков (одноразовая, в этом же этапе):** из `snapshot_positions`
  перенести цену за штуку = `value_rub / quantity` в `price_history` с
  `source = 'snapshot'`, валюта RUB. Для инструментов с ручной ценой это единственная
  история — потерять её нельзя. Сделай это миграцией/скриптом с тестом, не руками.
- Тесты провайдеров — на зафиксированных ответах ISS/ЦБ/Binance (как `moex.provider.spec.ts`),
  без сети.

### Этап 3. `valuationSeries` в ядре

- Чистая функция в `libs/core/src/lib/valuation.ts`: вход — операции, история цен,
  история курсов, опции (`from`, `till`, `groupBy: 'portfolio' | 'system' | 'instrument'`,
  фильтры); выход — по дням: вложено, рыночная стоимость, зафиксированный результат,
  переоценка, итог; флаг/список инструментов, у которых цена на день взята не за этот
  день (forward-fill) или отсутствует.
- Оценка позиции на день — **тем же кодом**, что текущая оценка (`marketValueRub` в
  `engine.ts`: НКД, валюта цены vs валюта инструмента, фьючерсы = нереализованный, а не
  стоимость). Не дублировать логику оценки.
- Позиции на каждый день — последовательным проходом по отсортированному журналу
  (`operation-order.ts`), без пересчёта всего журнала на каждый день (O(дни × позиции),
  не O(дни × операции)).
- Деньги — `Decimal`, наружу decimal-строки.
- Инварианты (тесты):
  - точка «сегодня» при текущих ценах = текущая сводка (`/api/operations/summary`);
  - сумма рядов по системам = ряд портфеля (по каждому дню);
  - без цен (пустая история) зафиксированная часть совпадает с этапом 1.
- Краевые: инструмент без единой цены; переворот фьючерса; валютная облигация (цена в
  USD, НКД в ₽); перевод между портфелями (`Transfer`); операция задним числом меняет
  только дни ≥ её даты.

### Этап 4. Переключение потребителей

- API: эндпоинт ряда (например, `GET /api/valuation/series?groupBy&systemId&portfolioId&from&till`)
  с Zod-DTO в `schemas.ts`. Перед расчётом — `PriceHistoryService.ensure`.
- Страница системы: «Результат системы» строится по `valuationSeries` (этап 1 остаётся
  как зафиксированная часть этой же кривой, не параллельный код). **Просадка, Sharpe,
  Sortino, recovery factor** считаются по дневной кривой; метрики сделок — по закрытым
  сделкам, как сейчас. В DTO разделить `tradeMetrics` и `equityMetrics`, у каждого
  подписан базис.
- Дашборд: `benchmark-chart` («Вложено vs Текущая стоимость») и
  `positions-series-chart` («Стоимость инструментов во времени») — на `valuationSeries`.
  `entities/snapshot`, `entities/position-series` заменить на `entities/valuation`.
- Участки кривой с forward-fill/без цены — визуально помечены (тултип «цена на дату
  не найдена, взята от …»).
- Кнопку «Сделать снимок» на дашборде убрать: её роль выполняет «Обновить цены».

### Этап 5. Сверка со старыми снимками (до удаления)

- Одноразовая проверка (скрипт или спек на реальной БД, не новая фича UI): для каждой
  даты `portfolio_snapshots` сравнить с `valuationSeries` по портфелю. Вывести таблицу
  расхождений > 1 ₽ с вероятной причиной (снимок помечен устаревшим журналом
  `snapshot_invalidations` / нет цены в истории / иное).
- Результат приложить в отчёт пользователю. Если есть расхождения без объяснения —
  **остановиться и спросить**, не переходить к этапу 6.
