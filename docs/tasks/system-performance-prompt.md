## 1. Цель

Страница «Система» (`/systems/:systemId`): подробная статистика результатов торговли по
**любой** торговой системе (`systems` — справочник, у каждой операции есть `systemId`).
Пример — система «ЮВ1», фьючерс `CNY-12.26` (шорт днём, выход утром следующего дня), но
ничего специфичного для ЮВ1 в коде быть не должно: та же страница работает для системы
на акциях/облигациях/ETF.

Данные — **уже существующие**: операции из отчёта брокера (HTML) → движок `@core`
`calculateTrades` собирает сделки (цикл «позиция открылась → ушла в ноль»). Дополнительные
данные исполнения (сигнальная цена, причина входа, проскальзывание) пользователь
может дать отдельным CSV — это **необязательное обогащение** (этап 5), без него страница
должна работать полностью.

Модель, которую задал пользователь: **источник сделок любой** (HTML-отчёт брокера, API
брокера как у Т-Банка) → итог всегда один — журнал операций, сделки привязаны к системе.
Если в первичном источнике чего-то нет (комиссия придёт позже, отдельной строкой), это
**дообновляется** у уже существующей операции, а не создаёт дубль (этап 4).

## 1a. Что уже есть в отчёте брокера (проверено на `SESPS_31102024_05112026.HTML`)

| Данные | Где в отчёте | Достаточно? | Как используем |
|---|---|---|---|
| Сделки по фьючерсу (дата, время, сторона, кол-во, цена, № сделки) | «Срочные сделки» | да | операции журнала (уже парсится) |
| Комиссия по каждой сделке | там же: «Комиссия Брокера» + «Комиссия Биржи» | да, это **фактические** суммы | `fee` операции (уже парсится). Биржевая колонка уже включает клиринговый сбор: 1,32 + 0,96 = 2,28 в CSV = 2,28 в отчёте |
| Комиссии строками «Комиссия Брокера от …» | «Движение ДС» | дублируют колонки сделок | пропускаются — правильно, иначе двойной счёт |
| Вариационная маржа по дням | «Движение ДС»: «Зачисление/Списание вариационной маржи по CNY-12.26» | неполная: проводится на следующий клиринговый день, за последние дни периода её ещё нет | **не входит в P&L** (способ А, docs/02); используется только для сверки (этап 4) |
| ВМ за период и плановая ВМ | «Срочный рынок»: 204,00 и −11 117,00 | да | сверка: результат по сделкам + нереализованный = ВМ факт + плановая |
| Расчётная цена на конец периода | «Срочный рынок»: 12,387 | да | нереализованный результат (уже сохраняется в `quotes`) |
| Гарантийное обеспечение (ГО) | нет | — | метрики в % от капитала/ГО не строим (см. §5) |
| Сигнальная цена, причина входа (h1/h2/exit) | нет | — | только из CSV QUIK (этап 5) |

Ключевые факты сверки:
- **Номер сделки в отчёте = `trade_num` в CSV QUIK** (например, `2022430697309901475`) →
  сопоставление по `brokerRef` точное, эвристика по дате/цене не нужна (оставь только
  как диагностику «не найдено»).
- **Комиссия брокера в CSV QUIK — оценка терминала, не факт**: 19,54 ₽ в CSV против 7,40 ₽
  в отчёте за ту же сделку. Отчёт — источник истины для комиссий; комиссии из CSV
  никогда не перезаписывают комиссии из отчёта/API.
- Отчёт сверен с движком: результат по ценам сделок + нереализованный = −10 913 ₽ =
  ВМ отчёта (204 − 11 117); сумма комиссий 962,91 ₽ = итог колонок отчёта (737,23 + 225,68).

**Вывод: для статистики по ЮВ1 данных отчёта достаточно**; дополнительно нужны только
(а) механизм дообновления операций для источников, где комиссия приходит отдельно/позже,
(б) сверка с ВМ, (в) необязательные данные исполнения из CSV.

## 2. Архитектура (как это ложится на проект)

Поток данных — как у существующего `/api/operations/summary`:

```
operations (БД) ──► @core calculateTrades ──► @core systemPerformance(...)  ← чистая функция
                                                      │
              GET /api/systems/:systemId/performance  │  (NestJS, Zod-DTO, decimal-строки)
                                                      ▼
   entities/system-performance (httpResource + parse) ──► pages/system ──► widgets/*
```

Принципы:

- **Вся математика — в `libs/core`** (SRP, DRY, тестируемость). Ни контроллер, ни
  компонент метрики не считают. Компонент только форматирует.
- **Деньги — `Decimal`** внутри расчёта, наружу — decimal-строки (как во всём
  `schemas.ts`). Безразмерные коэффициенты (win rate, profit factor, Sharpe) — `number`.
  Существующий `tradeStats` в `metrics.ts` суммирует `number` — не копируй этот подход
  для денег; переиспользуй/расширь так, чтобы не было двух разных формул win rate
  (одна реализация, `trades.page.ts` и `widgets/trade-stats` переводятся на неё или
  остаются на `tradeStats`, который становится тонкой обёрткой над новой функцией).
- **Одна точка истины для сделки** — `TradeResult` из `engine.ts`. Не заводи
  параллельную «сделку стратегии».
- **Фьючерсы не особый случай в метриках.** Различие инструментов уже скрыто в движке
  (`applyFutureFill`); метрики работают с результатом сделки в ₽.
- FSD: `entities/system-performance` → `widgets/system-*` → `pages/system`. Импорт только
  вниз. Nx-границы не ломать.
- Без новых зависимостей (графики — уже подключённые Chart.js/ng2-charts через
  `widgets/chart-canvas`, `shared/chart.providers.ts`).
- Angular: standalone, OnPush, `input()/output()`, `inject()`, signals/`computed`,
  `@if/@for(track)`, `httpResource` с `parse: Schema.parse`. Сверься с Angular CLI MCP
  (`get_best_practices`) перед написанием компонентов.

## 3. Этапы (каждый — атомарный коммит, тесты зелёные)

### Этап 1. Ядро: `libs/core/src/lib/performance.ts` (+ `performance.spec.ts`)

**1.1. Доработка сделки (минимально необходимое):**
- `direction: 'Long' | 'Short'` у `TradeResult` и `TradeSchema` (для не-фьючерсов
  всегда `Long`). Фьючерсный шорт определяется по знаку позиции при открытии.
- Время открытия/закрытия: `openedAt`/`closedAt` сейчас — только дата, у внутридневных
  фьючерсных сделок срок удержания в днях бессмысленен. Добавь `openedTime`/`closedTime`
  (из `executedAt`, nullable — у старых операций пусто) и считай срок удержания в часах,
  если время есть, иначе в днях. Не ломай существующие потребители.
- `feesRub` по сделке (сумма комиссий всех её операций) — нужна для «доли комиссий».
- Проверь, что `realizedPnlRub` у фьючерсной сделки уже за вычетом комиссий (по
  `docs/02` — да); у обычных — комиссия покупки в себестоимости, продажи — в выручке.
  Метрика «gross» = net + fees.

**1.2. `systemPerformance(trades, options)`** — чистая функция, вход — сделки одной
системы (фильтрацию по системе/портфелю/периоду делает вызывающий или опции):

| Блок | Метрики |
|---|---|
| Итог | net P&L ₽ (реализованный), нереализованный по открытым, комиссии ₽ и их доля от gross P&L |
| Сделки | всего закрытых, прибыльных, убыточных, в ноль; win rate %; лонг/шорт отдельно |
| Качество | средний выигрыш/убыток, payoff ratio (ср. выигрыш / \|ср. убыток\|), profit factor, матожидание ₽ на сделку, крупнейшие выигрыш и убыток |
| Серии | макс. подряд прибыльных / убыточных, текущая серия |
| Риск | макс. просадка ₽ по кривой эквити (пик, дно, дата восстановления или `null`), длительность просадки в днях, recovery factor = net / \|maxDD\| |
| Время | средний срок удержания (часы/дни), ср. срок прибыльных vs убыточных |
| Ряды | кривая эквити (накопленный net P&L по дате закрытия, точка на день), ряд просадки, P&L по месяцам, P&L по дням недели, гистограмма результатов сделок |
| Отношения | Sharpe и Sortino по **дневному** P&L в ₽ (без капитала — это корректно как отношение среднего к σ; годовая нормировка √252; дни без сделок = 0 между первой и последней датой). Подпиши в DTO формулу/допущения |

- Дату точки эквити бери по дате закрытия сделки; последняя точка — «сегодня» с учётом
  нереализованного по открытой позиции (отдельным полем, не смешивая с реализованным).
- Метрики в % от капитала (доходность, CAGR, просадка %) **не делай** — капитала у системы
  в модели нет. Вынеси в «Открытые вопросы» отчёта (см. §5), не добавляй поле в БД сам.
- `maxDrawdown` в `metrics.ts` работает с рядом стоимости (пик > 0) — для ряда P&L,
  стартующего с 0, нужна абсолютная просадка: добавь отдельную функцию, существующую
  не меняй по смыслу.

**1.3. Тесты (Vitest, обязательны — это финансовая логика, CLAUDE.md §10, §11):**
- Эталон на реальном отчёте `SESPS_31102024_05112026.HTML` («Срочные сделки», `CNY-12.26`,
  цена ×1000). Комиссии — фактические из отчёта (брокер + биржа):
  - цикл 0 (лонг): Buy 2 @ 12 270 + Buy 2 @ 12 284 (29.10) → средняя 12 277; Sell 4 @ 12 328
    (30.10 10:20) → **+204 ₽** gross, комиссии 19,30 ₽ → net **+184,70 ₽**;
  - цикл 1 (шорт): Sell 4+3+58 @ 12 357 и 65 @ 12 340 (04.11) → средняя 12 348,5;
    Buy 81+25+20+4 @ 12 467 (05.11 10:20) → **−15 405 ₽** gross, комиссии 632,16 ₽ →
    net **−16 037,16 ₽**;
  - цикл 2 (шорт, **открыт** на конец отчёта): Sell 64 @ 12 421 + 52 + 12 @ 12 420 (05.11)
    → −128 по средней 12 420,5; расчётная 12 387 → нереализованный **+4 288 ₽**, комиссии
    311,45 ₽ уже в результате.
  - Сверка: −15 405 + 204 + 4 288 = **−10 913 ₽** = ВМ 204 + плановая −11 117; комиссии
    19,30 + 632,16 + 311,45 = **962,91 ₽**.
  - Метрики по закрытым: 2 сделки, win rate 50%, profit factor 184,70 / 16 037,16, payoff,
    макс. просадка от пика +184,70 до −15 852,46 … досчитай руками и зафиксируй в тесте.
  - Продолжение из CSV QUIK (появится со следующим отчётом): выход цикла 2 — Buy 128 @
    12 405 (06.11 10:20) → **+1 984 ₽** gross. Тест «цикл закрывается следующим импортом».
- Краевые: нет сделок; только прибыльные (profit factor `null`); только открытые;
  переворот лонг→шорт; серия убытков; восстановление после просадки.

### Этап 2. API: `GET /api/systems/:systemId/performance`

- Query: `portfolioId?`, `from?`, `till?` (ISO-даты, как у `summary`). Валидация Zod.
- DTO — `SystemPerformanceSchema` в `libs/core/src/lib/schemas.ts` (общий контракт
  фронт/бэк). Деньги строками, коэффициенты числами, `null` где метрика не определена.
- Где жить: эндпоинт системы логично в модуле, где справочник систем
  (`PortfoliosModule`, `GET systems`), а сделки уже собирает `OperationsService`
  (`GET operations/trades`). Не дублируй загрузку операций и сборку `futureIds` —
  вынеси/переиспользуй существующий метод получения сделок, сервис производительности
  зависит от него через DI. Контроллер — тонкий (GRASP Controller).
- 404, если системы нет. Пустая система → валидный DTO с нулями/пустыми рядами.
- Тест сервиса (как `operations.futures.spec.ts`).

### Этап 4. Дообновление операций и сверка с вариационной маржой

**4.1. Повторный импорт обновляет, а не только пропускает.** Сейчас импорт
(`ImportService`, `makeDedupeKey`) помечает совпадение как `duplicate` и пропускает. Нужно:

- Если пришла строка с тем же `brokerRef` (и тем же портфелем), что у существующей
  операции, но отличаются поля, за которые отвечает брокер (`fee`, при необходимости
  `executedAt`/`price`/`quantity`), — новый статус предпросмотра `update` с диффом
  «было → станет». При подтверждении операция обновляется (система, заметки и прочая
  разметка пользователя **не трогаются**). Полное совпадение — по-прежнему `duplicate`.
- Правило приоритета источников — одна политика в `libs/core` (например,
  `mergeBrokerFields(existing, incoming)`), а не `if` по месту: отчёт/API брокера
  авторитетны для денег и количества; CSV QUIK не меняет никаких полей операции.
- Комиссия, пришедшая **отдельной операцией со ссылкой на сделку** (так делает API
  Т-Банка: `OPERATION_TYPE_BROKER_FEE` с `parentOperationId`), должна прибавляться к
  `fee` родительской операции по `brokerRef`, а не висеть отдельным `Fee` без
  инструмента (иначе её не видно в сделке и статистике системы). Сделай это общим
  шагом нормализации `RawRow` (поле вида `parentBrokerRef`), чтобы им мог пользоваться
  любой парсер. Поддержку фьючерсов в парсере Т-Банка **не делай** в этой задаче — только
  убедись, что модель её допускает, и отметь в roadmap.
- Пересчёт снимков/инвалидаций после `update` — так же, как после импорта
  (`snapshot_invalidations`), не новым механизмом.
- Тесты: повторный импорт того же отчёта → 0 изменений; отчёт с изменённой комиссией →
  `update` на 1 строку; комиссия отдельной строкой по ссылке → прибавлена к родителю.

**4.2. Сверка с вариационной маржой** (контроль качества данных, не источник P&L).
- Парсер отчёта уже видит ВМ в «Движении ДС» и «Срочном рынке», но выбрасывает. Отдавай
  её отдельным результатом парсера (рядом с `marks` в `BrokerReportParseResult`): по
  инструменту и счёту — ВМ за период и плановая ВМ на дату конца отчёта.
- Хранить отдельной таблицей (`futures_settlements`: портфель, инструмент, дата конца
  периода, `vm_period`, `vm_planned`, источник), upsert по (портфель, инструмент, дата).
  В `operations` и в P&L **не попадает**.
- В `@core` — функция сверки: результат движка по инструменту в портфеле (реализованный
  gross + нереализованный по расчётной цене) за период отчёта vs `vm_period + vm_planned`.
  Расхождение больше 1 ₽ → предупреждение с суммой.
- ВМ привязана к счёту и инструменту, а **не к системе** (одним контрактом на одном счёте
  могут торговать две системы) — поэтому сверка показывается на странице «Портфель»
  у позиции фьючерса (маленький индикатор «сверено с брокером / расхождение N ₽»), а на
  странице системы — только если весь инструмент в портфеле принадлежит одной системе.
- Тест на эталоне §1.3: расхождение 0.

### Этап 5. Обогащение данными исполнения из CSV (опционально по данным, обязательно по коду)

Пример файла пользователя (`~/quik_bridge/from_quik/yv1_trades.csv`):

```
date,time,contract,side,qty,price,reason,ref_price,slip_rub,slip_pct,broker_fee_quik,exchange_fee,clearing_fee,techcenter_fee,order_num,trade_num
2026-11-05,13:00:04,CRZ6,S,64,12.421,h1,12.422,64.00,0.0081,314.71,21.12,15.36,0.00,...,2022430710194950984
```

Цель — **не второй журнал сделок**, а аннотации к уже импортированным операциям:
тег (причина входа/выхода: `h1`, `h2`, `exit`), сигнальная цена (`ref_price`) →
проскальзывание считается в `@core`, а не берётся из файла (`slip_rub` — только для
сверки в тесте).

- Хранение: отдельная таблица `operation_annotations` (1:1 к `operations.id`, поля:
  `tag`, `signal_price` decimal-строкой в ₽ за контракт, `source`, `imported_at`) +
  Drizzle-миграция. Журнал операций не засоряем полями одной системы.
- Сопоставление с операцией — по `brokerRef` = `trade_num` (совпадение проверено, §1a).
  Код контракта QUIK (`CRZ6`) ≠ тикер отчёта (`CNY-12.26`) — он нужен только для
  проверки согласованности (сторона, кол-во, цена должны совпасть с операцией; иначе
  строка — ошибка с причиной). Маппинг кодов положи рядом с `FUTURES_SPECS`, не хардкодом.
- Колонки комиссий CSV (`broker_fee_quik`, …) — оценка терминала, **игнорируются**
  (факт — в отчёте, см. §1a). `slip_rub`/`slip_pct` — только для сверки в тесте.
- Цены CSV в котировке → переводить тем же `scaleByPowerOfTen` (CLAUDE.md: не float).
- Парсер — Strategy/OCP: интерфейс `AnnotationParser` в `libs/core`, реализация под
  формат QUIK-выгрузки; новый формат = новый парсер. Не сопоставленные строки (например,
  первая строка файла закрывает позицию, открытую до начала выгрузки) — показать
  пользователю с причиной, не терять молча (как `skipReason` в импорте).
- Эндпоинт в `ImportModule` (предпросмотр → подтверждение, как существующий импорт);
  UI — секция на странице Импорт.
- В `systemPerformance` — блок «Исполнение» (появляется только при наличии аннотаций):
  суммарное проскальзывание ₽, среднее на контракт, по тегам; статистика сделок по
  тегу входа. Тест: проскальзывание по строке `h1 64 @ 12.421, ref 12.422` = 64 ₽.
